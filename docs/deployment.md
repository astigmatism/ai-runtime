# Deployment and recovery

The source repository is now `ai-runtime`. Existing production paths and the `local-ai-runtime` container/Compose project remain intentional compatibility names. Read [rename compatibility](renaming.md) before changing an existing Git remote; the first update must use the remote accepted by the deployed updater.

## Initial staging: no production service changes

The current source offers `qwen27b-q8-pair` and `qwen27b-q6k-pair` (160K, each with the everyday resident at 96K), and the solo `flash-next-strata-solo-thinking-recovery-cache` (160K, one resident across all four text GPUs), with `flash-next-strata-solo-thinking-recovery` beside it -- the same launch with the parked-conversation cache off, one switch away for a rollback. The configurations were renamed and consolidated on 2026-10-07, renamed again on 2026-10-15, and cut from five Strata configurations to two on 2026-10-18, after the two levers the five offered had been measured on this box. The [README](../README.md#current-configurations) maps the old names, and history below keeps the names in effect when it was written. The initial migration from the legacy primary deployment is complete. Its legacy `daytime` and `daytime-27b` configurations are retired, so `scripts/migrate.sh prepare` now refuses before writing private state.

Run on Rosalina as the existing deployment user after the repository is published:

```sh
git clone https://github.com/astigmatism/ai-runtime.git /home/astigmatism/apps/local-ai-runtime
cd /home/astigmatism/apps/local-ai-runtime
scripts/migrate.sh prepare
revision=$(git rev-parse HEAD)
docker build --build-arg SOURCE_REVISION="$revision" -t "local/ai-runtime:git-$revision" .
docker run --rm "local/ai-runtime:git-$revision" python3 -m unittest discover -s tests -v
scripts/migrate.sh inspect
```

`prepare` writes private state only in the new checkout. It imports the selected configuration, GPU UUIDs, directory locations, and the router token. It checks that the published Compose generation exactly matches the existing source. It does not change the old controller, router, wrappers, or model servers.

`inspect` runs a disposable image against read-only state/model/catalog mounts. The inspection code rejects Docker or HTTP mutations. It first verifies engine identity, live arguments, both slots, and existing checksum receipts. If every artifact has a previously verified SHA-256 with unchanged size, modification time, change time, and inode, it reuses those receipts. Otherwise it fully hashes the selected artifacts before recording `.state/inspection.json`. Live configuration drift fails before the expensive hash pass. It does not generate text, drain requests, publish a catalog, or restart anything.

Full hashing of the Flash-Next configuration reads every weight shard it declares — 33 for the llama.cpp layout this migration inspected, three for the Strata resident — plus any projector and draft. Schedule this disk-intensive verification when it will not compete with production work. Lightweight read-only inspection without `--full-hash` checks existing receipts, artifact sizes, per-service engine identities, arguments, mounts, health, and slot capacity; it cannot certify new checksums or substitute for the migration inspection gate. Importing historical hashes never creates a verification or performance-qualification receipt.

The status page and portal entry start during cutover, not during staging. Never publish `.state/`, `.env`, historical rollback directories, or raw production logs.

## Cutover: requires its own production authorization

Before cutover, review the inspection report, publish the Service Portal friendly-name change, and publish the router integration that respects `runtime-owner.json`. A controller image/source revision mismatch or any change to the inspected legacy files/backend identities stops the migration before cutover. Both saved profile directories and the `daytime-27b` wrapper are included in the migration baseline and backup. If generations must remain uninterrupted, defer cutover: it temporarily pauses new router admissions even when backend settings are unchanged.

```sh
cd /home/astigmatism/apps/local-ai-runtime
scripts/migrate.sh cutover
docker exec local-ai-runtime python3 -m runtime check
```

The cutover:

1. Acquires the old profile lock and checks the inspected files and backend IDs.
2. Saves private backups of the old scripts, registry, selection, and startup unit.
3. Adopts the exact healthy pair, briefly drains accepted work for verified catalog publication, and starts the controller with a bounded health wait.
4. Confirms both inference container IDs remain unchanged.
5. Replaces the old all-GPU deployment launcher with a refusal stub, then disables `local-ai-primary.service` only after the new controller is healthy. The old launcher previously depended on that unit's enablement for its safety guard; it must remain blocked after the unit is retired. Initial migration restoration restores its original bytes.
6. Installs home-folder wrappers and guarded legacy entrypoints, then writes `runtime-owner.json`.

The existing Service Portal server already supports the required update labels. Deploy its friendly-name mapping through its normal updater; no inference restart is involved. The controller's published HTTP port gives the portal a link, including when “Hide services without links” is enabled. The GPU containers remain hidden.

Check the new page, `/api/status`, `/healthz`, Service Portal's row/update capability, compatibility commands, backend IDs, router model discovery, and a short request to each resident service. The initial no-change portal update verifies runner execution and health; changed-release and rollback smoke tests must be performed only within the approved maintenance scope.

## Routine releases

The updater accepts clean `main` with the expected `origin/main` upstream and this repository's origin. It fetches public HTTPS and requires fast-forward history. It exports committed source into private release directories, builds/tests the image, validates Compose and model prerequisites, then applies the selected configuration under the runtime lock.

New router admissions pause during maintenance. Existing active, queued, and direct backend work must finish within five minutes; otherwise the change aborts before stopping a backend. An idle changed backend is recreated with `--no-deps --pull never --wait`. An unchanged backend is verified by identity and preserved. Generation acceptance uses an explicit eight-token test request without changing the model's output defaults.

After publication, the new controller is recreated with a 150-second health bound. The updater records image/commit/configuration identity and advances the checkout by fast-forward. No command performs Compose `down`, Git reset/stash, global pruning, or volume removal. A controller-only release retains the existing inference containers.

If a new revision retires the configuration currently active on a host, the updater refuses before building the candidate and names the retired configuration and the configurations selectable in that revision. Switch the active configuration to one of them on the deployed revision (runtime page validated transition), then re-run the update. The deployed runtime keeps serving meanwhile; no manual state editing is required. A rename is not a retirement: `PROFILE_ALIASES` maps a renamed id to its new one, so a release whose only crime is renaming the configuration that happens to be running is accepted, while `RETIRED_PROFILES` maps a retired id to its replacement and refuses.

## Browser configuration changes

The runtime page can select any registered configuration without another source release once it is published. Each choice shows its coding resident and, when the configuration loads one, its everyday resident, along with the GPUs each uses. Names come from the profile files through `/api/status`, so the page needs no code change when a configuration is added or renamed. Browser changes acquire the existing update and runtime locks and use the deployed controller's validated transition. They never edit source or advance a checkout. An unexpected everyday-resident replacement is refused, including during automatic recovery. The one exception is a switch into or out of a solo configuration, which deliberately removes or recreates the everyday resident (see below). Source deployments and existing CLI administration retain their existing behavior.

A rename is one release. The target revision maps the old id to the new one in `PROFILE_ALIASES`, and the updater accepts a release whose active configuration is recorded only under its old name; the new revision resolves that recorded id to the new one on every read. `tests/fixtures/renamed-profiles.json` records each renamed configuration's Compose digest, so a rename cannot change a backend. A retired id has no such pass: it refuses, and `RETIRED_PROFILES` says what to select instead.

The sections below are the history of the retired and renamed configurations: `daytime`, `daytime-flash-f16`, `daytime-27b`, `daytime-flash-next`, `daytime-flash-solo`, and `daytime-flash-solo-tuned`. `daytime-27b-tensor-next` is `qwen27b-q8-pair`; `daytime-flash-solo-tuned-mtp3` became `flash-next-solo-128k` and was retired on 2026-10-15.

`daytime-27b-tensor-next` is the saved Q8 `daytime-27b` with only `--split-mode tensor` overriding the shared `layer` split and `--tensor-split` moved from 60,40 to 55,45. In layer mode the RTX 3090 and RTX 4080 SUPER each run their share of the layer stack in turn for every token, so per-step time is the sum of both cards' weight reads. Tensor mode divides each weight tensor between the cards by the `--tensor-split` proportions so both read concurrently, at the cost of per-layer synchronization over PCIe (Gen3 x16, no NVLink); the pinned engine ships NCCL. The pinned engine (`8ea2902`) enables tensor mode for the `qwen35` architecture, including its recurrent-layer state, and requires flash attention, which is already on. It always places the MTP draft with layer split, and the unchanged `--spec-draft-device CUDA1` keeps it on the RTX 3090; `--fit off` is required because automatic fitting is not implemented for tensor mode. Because both cards read at once, each step lasts as long as the slower card's share, so the split should balance memory bandwidth (RTX 3090 936 GB/s, RTX 4080 SUPER 736 GB/s), not VRAM capacity. Monitoring at 60,40 showed the RTX 3090 at 91% SM and 72% memory-bandwidth utilization and at its 420 W power cap while the RTX 4080 SUPER sat at 75% and 50%; 55,45 moves about 1.45 GiB of Q8 weights to the RTX 4080 SUPER, which keeps roughly 0.6 GiB free at full context. Weights, Q4_0 MTP3 draft, q8_0 K/V cache, 160K context, batch sizes, projector, and RAM prompt cache are unchanged. A retired variant (2026-10-04) moved the MTP draft to the RTX 4080 SUPER at 60,40 and 128K: it loaded with about 0.85 GiB free on that card and moved the per-step bottleneck from the RTX 3090 (77% SM, ~367 W, off its power cap) to the RTX 4080 SUPER (90% SM), but steps per second were unchanged (24.73 vs 24.80–24.92), so it saved power without adding speed and gave up 32K of context. Its alias `qwen3.8-27b-q8_0-tensor-next` keeps benchmark history apart from the layer-split profile; the `daytime` and `local-active` service IDs are unchanged. On engine `836d571` it measured 26.1 steps per second on a full Bench Studio coding session (2/2 passed), against 24.8–24.9 for the same placement on the retired `8ea2902` engine; VRAM use was unchanged (21.6 GB RTX 3090, 15.6 GB RTX 4080 SUPER).

`daytime-27b-q6k-tensor-next` is `daytime-27b-tensor-next` with Unsloth UD-Q6_K_XL main weights (the former `daytime-27b-q6k` artifact); everything else is identical. It measured 27.0 steps per second (2/2 passed), about 3.5% faster than Q8 because UD-Q6_K_XL is only about 13% smaller and costs more dequantization work on the power-capped RTX 3090, with 1.5–1.7 GB more free VRAM per card. Its alias is `qwen3.8-27b-ud-q6_k_xl-tensor-next`. The layer-split `daytime-27b-q6k` and the `8ea2902` tensor profiles `daytime-27b-tensor` and `daytime-27b-q6k-tensor` were retired on 2026-10-04.

`daytime-flash-next` is `daytime` (Flash-Next AtomicChat AD-4.27bpw, 128K) on engine `qwen38-dual-836d571` instead of `flash-next-mtp`. The `flash-next-mtp` engine (`d1a92352c`) is an unmerged MTP branch on 2026-09-03 master. Upstream has since landed qwen4exp work that it lacks: the GDN normalization fix (#28068), fused hyper-connection ops (#28901), CUDA sparse attention above 32K context (#28770), PLE row prefetch for lazy mode (#29599), the attention-path fix (#29751), mask optimizations (#29824), halved indexer score memory (#29825), and its own MTP (#29761). Upstream MTP replaced the branch's (#28243, closed) and cannot borrow the target's embedding and output tensors, so the `shared-Q4_K_M` head cannot load on this engine (`token_embd.weight not found`). The profile therefore uses ggml-org's self-contained `mtp-Qwen3.8-Flash-Next-Q4_0.gguf` (revision `052beeac`, 2,199,652,640 bytes), converted by #29761. Its tensors match the unsloth heads, and its metadata marks the MTP block as a QSA layer. Only the engine, the alias `qwen3.8-flash-next-ad4.27-next` (separate benchmark history), the MTP head, the capability name, and the warnings change. Layer split, the 16,33 split on `CUDA1,CUDA0`, all 33 tensor overrides, 49 GPU layers, lazy mode, 2048 batch/microbatch, 18 threads, q8_0 K/V, MTP2 on CUDA0, the projector, and the shards are identical. The new head adds about 0.3 GB on the RTX 4080 SUPER, which had about 1.8 GiB free on `daytime`. Load, full-context VRAM headroom, and throughput are unqualified. A missing head or checksum mismatch refuses the switch before drain, and a failed load restores the previous profile.

Tensor mode is deliberately not used for Flash-Next. `flash-next-mtp` rejects it for `qwen4exp` outright; 836d571 re-enables it (#28569), but the placement works against it. Experts for 31 of 48 blocks (about 32 GiB) are in system RAM, and a FlashNext Bench Studio session decoded at about 31.5 tokens per second with a median step near 71 ms, against 25–35 ms for the 27B profiles. Tensor mode only divides the GPU-resident share of each step. The meta device it uses implements no `offload_op`, so the scheduler stops moving CPU-resident expert matmuls to the GPU for prompt batches: those 31 blocks would be computed on the CPU during prompt processing, which the 2048 microbatch is sized to avoid. Per-GPU overrides such as `blk.15.ffn_down=CUDA0` are unavailable because there is only the meta device and the CPU. Mirrored tensors (hyper-connection mixers, router gates, the indexer cache) are duplicated on both cards, which would push more expert blocks to the CPU. Upstream issue #27964 also reports `-sm tensor` asserting with this exact AD-4.27bpw quant on an earlier build. Tensor mode would be worth revisiting if the meta device gains op offload, or if enough VRAM keeps the experts off the CPU.

Engine `qwen38-dual-836d571` runs every Qwen3.8-27B backend: the everyday resident and both paired configurations. It also ran the saved `daytime-27b`, both tensor profiles, and the `daytime-flash-next` Flash-Next experiment. It is llama.cpp `836d57176dc699a726c55418e4f96b8ca628e1bf` (2026-10-03), the newest commit then with every CUDA CI job green, and is 460+ commits newer than the retired `8ea2902` engine (`qwen38-dual`), including the Qwen3.5 tensor-parallel split-state fix for fused QKV (#28965), CUDA graphs for the MTP draft (#28549), the AllReduce inactive-shard change (#29793), and speculative-decoding fixes (#29019, #29638). The image is built on the host from upstream `.devops/cuda.Dockerfile` at that commit, unmodified: `docker buildx build --target full --build-arg CUDA_VERSION=12.8.1 --build-arg CUDA_DOCKER_ARCH="86;89" --build-arg APP_REVISION=<commit> --label org.opencontainers.image.revision=<commit> -t local/llama.cpp:qwen38-dual-836d57176dc6`, in a dedicated buildx builder that is removed afterwards with its base images. The build receipt is kept under `~/ops/reports/20261004-llama-engine-836d571/`. Retention: the engine image is kept while any configuration in `config/shared.json` references it, and when the last referencing configuration is retired it is removed after checking compose image references, `.state/active.json`, `.state/previous.json`, and running containers.

The everyday resident runs tensor-parallel across its RTX 4080 (CUDA0) and RTX 3080 Ti (CUDA1): `--split-mode tensor` with the existing `--tensor-split 60,40`, on engine `qwen38-dual-836d571`, which supports `qwen35` tensor mode and requires the flash attention and `--fit off` it already sets. At the time of this measurement it had no MTP draft; it has run MTP3 since 2026-10-07. Before the change it ran layer split at about 29.5 tokens per second, with the RTX 4080 at 15.7 of 16.4 GB and the RTX 3080 Ti at 10.8 of 12.3 GB in use. The two cards have similar memory bandwidth (716 and 912 GB/s), so 60,40 is a VRAM-capacity split that may leave the RTX 3080 Ti underused; its throughput and full-context VRAM headroom in tensor mode have not been qualified. Changing the everyday resident's placement recreates only that resident after drain; if it fails to load or verify, the update restores the previous release.

Every coding resident inherits the RAM prompt-cache cap from `config/shared.json` (`--cache-ram` 49152 MiB = 48 GiB). The everyday resident alone overrides it to 24576 MiB (24 GiB): on the 123 GiB host its cache had grown to about 50 GB, about 8 GB of it swapped out, with host swap exhausted, so the worst-case combined pair is bounded at 72 GiB instead of 96 GiB. The cap is a lazy LRU limit allocated on demand, never reserved; each model's catalog entry publishes its own `global_ram_prompt_cache_mib`. Changing the everyday resident's value recreates only it after drain and discards its in-memory prompt cache.

A controller-only release of the GPU overview and switching UI does not change rendered model definitions. Verify its revision, health, assignments, configuration choices, and disabled controls during other maintenance using read-only requests after deployment. Test an actual production configuration switch only in an agreed maintenance window; this pauses new admissions for both models and loads the alternative coding resident.

Operation receipts survive page refresh and controller restart. If a switch reports `needs-attention`, inspect the private journals and follow **runtime recover** below. Do not clear journals or edit selected-release receipts to make the controls available. No browser action cancels an in-progress transition or forces a backend restart. After recovery, the controller reconciles the operation result on its next status cycle.

## Exclusive solo configurations

`daytime-flash-solo` is `daytime-flash-next` (the same weights, projector, ggml-org Q4_0 MTP head, 128K context, q8_0 K/V, lazy n-gram table, and engine `qwen38-dual-836d571`) moved onto all four text GPUs with automatic fitting. `daytime-flash-solo-tuned-mtp3` is the recommended solo configuration of its generation: the measured tuning winners on engine `qwen38-dual-43fe9c6` with a three-token draft. `daytime-flash-solo-tuned` is the same with a two-token draft. All three set `"exclusive": true` and `"gpu_group": "all"`, so the everyday resident does not run while one is selected, and each keeps its own alias (`qwen3.8-flash-next-ad4.27-solo`, `-solo-tuned`, `-solo-tuned-mtp3`) for benchmark history. The three were retired on 2026-10-15, with the engine they were tuned on; `flash-next-strata-solo` is the solo configuration that replaces them, and the placement and transition rules below are the rules a solo configuration follows.

Why: on two GPUs, the experts of 31 of 48 blocks (about 32 GiB) live in pageable host memory.
- Every decode step reads the routed experts of those blocks from RAM, and MTP verification multiplies those reads. The Bench Studio session decoded at about 31.5 tokens per second, against about 90 for the 27B tensor profiles.
- Every prompt batch of at least 32 tokens (`GGML_OP_OFFLOAD_MIN_BATCH`) copies the used experts over PCIe Gen3, nearly all 512 per block. That is why the median first token was about 3.8 s even for small agent turns, against 0.9 s for the 27B.
- About 54.5 GB of the model must be resident; the attention cache is about 25 KB per token. That fits in the 68 GiB of the four text GPUs.

Placement:
- The renderer orders CUDA devices as `gpu_ids.daytime`, then `gpu_ids.nighttime`, then the vision GPU. On Rosalina that is CUDA0 RTX 3090, CUDA1 RTX 4080 SUPER, CUDA2 RTX 4080, CUDA3 RTX 3080 Ti, CUDA4 RTX 3080. On an argument-vector engine it exports that `CUDA_VISIBLE_DEVICES` order and reserves all five UUIDs. An environment-configured solo configuration reserves the same five devices and exports the indices `0,1,2,3,4`, which the container numbers in the host's own bus order; its language model is told `GPUS=0,1,2,3` and its encoder is placed by `vision_cuda_device`, so the shared card has to be the last one reserved.
- The language model uses `--device CUDA1,CUDA2,CUDA3,CUDA0`, so the RTX 3090 is last and holds the output layer.
- `daytime-flash-solo` uses `--fit on --fit-target 1024`, which distributes layers itself and counts the MTP draft. To reach full residency it splits two layers across devices with tensor overrides. The tuned profiles pin whole layers instead: `--fit off --n-gpu-layers all --tensor-split 11,12,8,18` (48 blocks plus the output layer). They use one host thread (`--threads 1 --threads-batch 1`; see host CPU use below). They load in about 35 s with no fitting search, and a load that does not fit fails loudly instead of spilling to the CPU. With F16 K/V, Rosalina keeps 1.3–2.0 GiB free on each text GPU.
- The microbatch is 1024. Large microbatches only paid for themselves while experts were streamed from the CPU. At 2048, fitting no longer kept every expert on the GPUs.
- The projector and the MTP draft use CUDA4; the vision GPU is not shared in this mode.
- Validation requires a configured `vision_gpu_id`, `--device` naming CUDA0–CUDA3 once each, and tensor overrides limited to CPU or CUDA0–CUDA3. That validation belongs to the argument-vector path: an environment-configured solo configuration validates instead that the host states `vision_cuda_device` as the index the shared card is numbered at, and that its profile leaves the text cards as `0,1,2,3`. A paired configuration can still never place text tensors or drafts on the vision GPU.

Transitions:
- **Into a solo configuration.** The controller drains both models and waits until both are idle. It stops and removes the everyday resident's container `qwen38-nighttime` (removal keeps its restart policy from reviving it on reassigned GPUs), then recreates the coding resident and publishes a one-model catalog. A request for a service ID nothing loaded publishes is answered from the catalog's `offline_services`, not by alias substitution. `flash-next-strata-solo` publishes no offline service, because its own resident answers `nighttime`.
- **Back to a paired configuration.** The coding resident is recreated first, so the solo container releases every GPU, and the everyday resident second. The everyday resident's in-memory prompt cache does not survive.
- **Failed switch.** Recovery follows the same order. Restoring a paired release recreates the coding resident and then the everyday resident. Restoring a solo release first removes any everyday resident the failed target started.
- **Drift.** A running everyday resident beside a solo release is reported as `competing everyday backend running`, and the next apply removes it.
- **Status.** `/api/status` reports `offline_roles: ["everyday"]` while a solo configuration is active. That is placement, not reachability: what a client cannot ask for is the catalog's `offline_services`, and `flash-next-strata-solo` leaves it empty because its resident answers `nighttime`. The page asks for confirmation before selecting a solo configuration.
- **Unchanged rules.** Browser switches between paired configurations still refuse to touch the everyday resident.

- **Retired:** the one-variable experiment configurations were retired after measurement; this table is their record.

Host CPU use (2026-10-06): the first tuned profiles kept the shared `--threads 18`, and decode then used about 9–11 CPU cores where `daytime-flash-solo` used one. Measurements on Rosalina:
- **Cause:** engine `43fe9c6` alone reproduced it. On the older engine, the pinned layout, MTP depth, lazy mode, and `--poll 0` changed nothing.
- **Where the CPU went:** a scheduler trace (`GGML_SCHED_DEBUG=2`, verbosity 5) showed the decode graph's CPU input split gained `DUP` and `SET_ROWS` nodes for the new mixed embedding-and-token batch input (llama.cpp #29622), next to the token and per-layer embedding `GET_ROWS`. The work is microseconds, but it now runs as an 18-thread OpenMP region several times per decode step. Between regions, libgomp workers busy-wait, so 17 threads sat at about 57% each.
- **Proof that this is only waiting:** `OMP_WAIT_POLICY=PASSIVE` cut decode CPU from 10.7 to 1.05 cores at the same speed. `--threads 1 --threads-batch 1` also gives about 1.0 core.
- **No cost to speed:** on the session replay, both tuned profiles with one host thread produce identical output at the same speed: 93.2 against 93.1 tokens per second for `-tuned-mtp3`, with identical 221 s wall time. CPU fell from 2055 to 224 CPU-seconds, about 118 to 13 ms of CPU per generated token. Prefill speed is unchanged (1124–1132 tokens per second at 32K).
- **Why one thread is enough:** every expert is on the GPUs. The remaining host work is driving the GPUs (the main thread, about one core in every solo configuration) and the tiny input split.

Concurrency and context experiments:
- **Two slots.** A configuration may set `"parallel_slots": 2`, and only a solo configuration may. The renderer then passes `--parallel 2`, sizes `--ctx-size` for both slots, and keeps `--kv-unified-per-slot` and the catalog `context_length` at the per-request window. The controller verifies the slot count and each slot's context.
- **Router admission follows the slots.** The catalog publishes `max_active_requests` as the slot count and `total_context_length` as the window times the slots. LLM Router `a2f3406` and later admits two overlapping requests for such a resident and queues the next. An older router rejects a two-slot catalog, and the switch then recovers to the previous configuration.
- **`daytime-flash-solo-tuned-mtp3-2slot`** (renamed `flash-next-solo-two-requests`, then retired on 2026-10-07; the two-slot capability remains): two 128K slots with q8_0 K/V, so the pool uses the same KV memory as one F16 slot, and a 512 microbatch. At microbatch 1024, a cold 32K prefill in one slot while the other decoded hit the same RTX 4080 `top_k` out-of-memory abort as F16 at 160K.
- **`daytime-flash-solo-tuned-mtp3-160k`:** the tuned profile with a 160K window and q8_0 K/V. With F16 K/V at 160K, the RTX 4080 kept about 0.8 GiB free, and a cold 32K–98K prefill aborted the backend. The CUDA out-of-memory error (`cuMemCreate`) came from the VMM pool in `top_k` (CUB argsort) for the sparse-attention indexer, scratch that the compute-buffer reservation does not include. Docker restarted the container, and no other backend was affected.

## Strata solo configuration (flash-next-strata-solo-thinking-recovery)

The Strata resident is an ordinary resident, added 2026-10-11 as a trial: the same four text GPUs and the same 163,840-token window as the retired `flash-next-solo-160k`, but the model served by [Strata](https://github.com/Niko1221/Strata) instead of llama.cpp, from Unsloth's dynamic 4-bit `UD-IQ4_XS` quant (93,682,584,224 bytes, revision `38bb39ee97821de2c9009abb7e93950eec396e66`). It exists to answer one question: whether Strata's profiled expert caching beats llama.cpp's resident layout where llama.cpp is weakest, which is decode in a long context (measured below: 97 tokens per second at 4K falling to 35 at 128K).

**The XL sibling** (`flash-next-strata-xl-160k`, added and retired on 2026-10-15) changed exactly one
variable: the same model at `UD-Q4_K_XL` (111,334,654,784 bytes in four shards, not three) on the same
engine, the same four cards and the same argument vector, reached through `trial-xl`. It was a second
configuration rather than an edit to the served one so that the comparison was a configuration switch
in both directions and the measured quant stayed live underneath it. What it tested was expert residency, not
bit depth: 0.1.44.1 writes no `--resident-budget-gib` when the experts fit beside 16 GiB of working set
(77.0 + 16.0 = 93.0 GiB against 123.2 GiB of RAM here), which on paper puts every expert in RAM and
deletes the cold path measured at 30–60% below warm.

**It lost on every cell, and so did the hypothesis.** With residency verified — 71.73 GiB of experts in
RAM, no budget flag — `UD-Q4_K_XL` measured 7–15% slower decode and 41% slower prefill than the serving
`UD-IQ4_XS`, gaps 2–10× the 3% this instrument resolves, on identical answer hashes. Residency was the
wrong cold path: the binding constraint is RAM→GPU PCIe streaming, which fatter experts worsen, and
residency only deletes disk→RAM reads. Decision: keep `UD-IQ4_XS`, do not re-run for speed. Full record
with data, timeline and audit at `ops/reports/20261015-strata-xl-trial-result/`; the 112 GB of shards and
workspace were released with the profile. Two things it found stay in source: sharing one engine across
two quants is what forced the ready marker in `provisioning` to stop naming a quant (see `ready_files`
in `runtime/provision.py`), and `$STRATA_ALLOWED_HOSTS` is how a Strata profile names the hosts its
server will answer to (see `tests/test_config.py`).

- **Its service IDs.** It declares `"aliases": ["local-active", "daytime", "nighttime"]`: those are the IDs a client sends for it — `GET /v1/router/capabilities` reports `models[].service`, and `POST /v1/chat/completions {"model": "daytime"}` resolves to this backend. It was added on 2026-10-11 under `trial`, its own ID and nobody else's; the 2026-10-15 rename came with the three contract IDs, because a solo configuration replaces the coding resident rather than adding a second one, so the IDs its clients already send have to be answered from it. Selecting it is still an explicit act, and only the owner does it.
- **Nothing is left unanswered, and one role is still not loaded.** Its catalog carries no `offline_services` entry: every service ID a client sends is answered by the resident that is up. `/api/status` nevertheless reports `offline_roles: ["everyday"]`, because the everyday role genuinely is not loaded — one resident answers `nighttime` from its own backend. The two fields answer different questions, `offline_services` what a client cannot ask for and `offline_roles` what the machine is not running, and this configuration is the case where they disagree.
- **Two properties, both tested** (`tests/test_config.py`, `ServiceIdentityTests`). Every selectable configuration has to publish a service alias a contract client can address: LLM Router names an entry by the first of its aliases that is not the compatibility alias and otherwise falls back to the canonical ID (`src/capabilities.js`), and a client forbidden from sending canonical IDs cannot ask for such a model at all — a backend that is healthy, selected, and impossible to reach. That hole existed: the configuration published `aliases: []` from 2026-10-11 to 2026-10-13 and the primary client on this machine had no model while it was selected. The other half is that a service ID belongs to one configuration at a time: the catalog is published from the selected configuration alone, so `daytime` never resolves to two backends.
- **The `c3a342b` requirement is dated.** That is the revision that stopped requiring a resident catalog's default entry to declare the `local-active` compatibility alias: the empty alias list this configuration carried from 2026-10-11 to 2026-10-13 was only publishable because of it. A router older than that refuses such a catalog as `INVALID_MODEL_CATALOG` — at publication, so after the drain, with the prior catalog written back and the switch restored rather than the host left drained. Publishing `local-active` directly means any router revision accepts this catalog.
- **Engine** `strata-296b59d2f73c` (since 2026-10-15): Strata `v0.1.44.1` at `296b59d2f73c8f04a805df29c2fa97655adace78`, image `local/strata:296b59d2f73c` (`2c6b8332effd…`), compiled for `sm_86,sm_89` on `nvidia/cuda:13.0.0-devel-ubuntu24.04` (`1e8ac7a5…`). No weights are in the image: it reads the mounted revision. It is built on this host because upstream's releases ship Windows zips only; the build is `ops/strata-build/build-image-0.1.44.1.sh`, one overlay layer above their own Dockerfile, receipt `ops/reports/20261015-strata-engine-0.1.44.1-build/`. The configuration moved to it from `strata-7695859aa13a` (`v0.1.43` at `7695859aa13a`, image `8d852ef69ad6…`), which stays registered while the candidate is under evaluation.
- **Engine `strata-vision-296b59d2f73c`** (since 2026-10-16): the same revision with its image encoder compiled in, image `local/strata:296b59d2f73c-vision` (`16ffa1282a12…`, the image before it kept as `local/strata:296b59d2f73c-vision-pre-recovery`), built by `ops/strata-build/build-image-0.1.44.1-vision.sh` with `--build-arg BUILD_VISION=1` and this repository's `runtime/overlay/` as the layer on top, receipts `ops/reports/20261016-strata-vision/`, `ops/reports/20261017-strata-sampling/` and `ops/reports/20261017-strata-tool-call-recovery/`. `BUILD_VISION` is decided at build time and is not a runtime switch, so one revision is two images and two engine entries, and undoing the encoder is a profile change rather than a rebuild. The overlay is what makes the encoder's card declarable at all: it moves upstream's entrypoint aside as `docker-entrypoint.upstream.sh`, writes `vision.cuda_device` from `VISION_DEVICE` into the run config that entrypoint is about to start, and execs upstream unchanged — behaviour pinned by `VisionEntrypointOverlayTests`. Since 2026-10-17 it writes two more things into that same file: the `sampling` block named by `SAMPLING`, and the top-level `tool_call_recovery` boolean named by `TOOL_CALL_RECOVERY`, which is what makes either of them declarable at all — neither has an argument in the engine. The tag was rebuilt for the second of the two on 2026-10-17; the image before it, which is what a container runs until the revision that pins the new id is deployed, ignores `TOOL_CALL_RECOVERY` the way it ignored `SAMPLING` before its own rebuild. The overlay is baked into the image and not mounted, so any change to it is a rebuild of this tag, a new `image_id` in `shared.json`, and a receipt naming the sha256 of the entry point that went in: the controller refuses a container whose image id is not the one the engine entry states, so those three move together or the boot does not happen. The encoder's weights are ISTA-DASLab's `mmproj-Qwen3.8-Flash-Next-BF16.gguf` (907,543,008 bytes, revision `ed59f92082b1e93c0e96d60a8b11aab089b52f09`), mounted beside the shards because `setup.py` looks in `GGUF_DIR` before it reaches for Hugging Face, so a fresh workspace still needs no egress.
- **What 0.1.44.1 was expected to change, and what it was not.** It was *not* taken for draft-acceptance work: the only drafter changes in 0.1.44 are AMD RDNA4-only, and 0.1.44.1 is a hotfix whose notes state its answers are byte-identical to 0.1.44, which makes the answer-hash gate a clean pass/fail. What it carries that this box can use is `STRATA_COMMIT_BATCH` (one commit-graph launch per layer kind, on by default, bit-identical) and the sm_86 dense-Q8_0 row-per-block path (+2.8-3.8% decode on UD-Q4, and two of the four cards are sm_86). It is also the enabler for `UD-Q4_K_XL`, which 0.1.43 still calls experimental and whose full-residency budget rule does not exist there.
- **One trap this version sets.** 0.1.44's `setup.py` writes `STRATA_HC_Q8=1` into the config's `env` block for Unsloth files on NVIDIA. That is the lever this house measured at decode +1.1% and **prefill -8.2 to -15.5%**, first token 9-18% slower, and answers changed, and reverted on 2026-10-14. A persisted engine config keeps it off; a config regenerated by `setup.py` (a fresh container, or `REINSTALL=1`) does not. Check the `env` block after any cutover that regenerates it.
- **It is not configured by flags.** The container's entrypoint reads its settings from the environment and writes its own engine config, logs and installed state. The engine therefore declares `"interface": "environment"` plus a map from each configuration argument to the variable the entrypoint reads, and is rendered from its own arguments alone; the llama.cpp vocabulary, the per-slot KV flags, and the artifact-only mount list are not applied to it. What follows from that, and what stayed:
  - The service has an empty command, `read_only: false` (its config link and logs go under `/opt/strata`), and one writable bind: `ai/strata-trial/data` at `/data`, where the engine keeps its expert pack, its MTP draft layer and its own logs. Every model file stays a read-only bind, and the mount check in `observe` now honours each mount's own read-only flag instead of assuming all of them are.
  - `GGUF_DIR` is derived from the mounted model path and `CONTEXT` from `context_tokens`, so the engine cannot be pointed at a revision the configuration did not checksum.
  - Its health and idle checks are unchanged: Strata answers `/health` and `/slots` in llama.cpp's shape. Its window is checked against the published configuration instead of the argument vector, the bounded generation probe runs in the OpenAI chat dialect (there is no `/completion` and no `/tokenize`), and the published output-policy record says `docker-inspect-env` because there is no argv to read a ceiling out of.
  - A fresh container reads all 94 GB of its shards, prepares its pack and installs its draft layer before it answers a health check, so the engine names its own readiness window (3600 s, and the same start period on the healthcheck) instead of inheriting the 450 s llama.cpp waits.
- **An engine's container settings are merged over the house ones, never in place of them.** This is the lesson of the trial's first switch attempt (2026-10-11, `ops/reports/20261011-strata-trial/FAILURE-20261011-switch.md`): the engine entry declared its own `container_defaults` — entrypoint, root, ulimits, healthcheck — and those *replaced* the shared defaults, so the service arrived with no restart policy, no init, no logging and no pull policy, and the observer died on `KeyError: 'restart'`. It failed closed, 93 GB of artifact checks in and no container touched: the active configuration never moved and nothing was stopped. Three things follow, and all three are in the code now: engine defaults are deep-merged over the shared ones before the configuration is merged over them (`merge_settings`); every rendered service is checked against `CONTAINER_CONTRACT` at render time, so a service that cannot state how it runs is a configuration error at deploy rather than a crash at switch; and `observe` reads every expectation with `.get()`, so a bundle that lost a key produces the named drift reason instead of an exception. The same observation pass runs over the four llama.cpp profiles with no new reasons, and they render byte-identically to the revision they were deployed on.
- **What the backend answers is checked, and a mismatch says what it saw.** At the pinned revision `/health` replies `{"status": "ok", "max_context", "model", "images", "api_key", "loaded", "service": "strata"}` and `/slots` replies a list of `{"id", "n_ctx", "is_processing", "n_prompt_tokens"}` — one entry per slot, or `[]` while the engine is not loaded. `n_ctx` is the window the *engine* loaded with, which is not necessarily the one asked for, so a window mismatch now records `slot_window` (`contracted`, `reported_context`, `loaded`) in the observation as well as the `slot context` reason: a backend that came up on a smaller window is permanent and must be readable, while an empty slot list is one still loading, and those two otherwise look identical while the switch sits out its health timeout.
- **Pre-flight that needs no switch and allocates nothing:** `docker run --rm --user 1000:1000 --gpus all --entrypoint /opt/strata/.venv/bin/python local/strata:7695859aa13a setup.py --check --yes` reports the engine's own verdict on the machine without installing or downloading anything (`ops/reports/20261011-strata-trial/preflight-strata-check.log`, 2026-10-11: all five cards usable, `[ok] RAM: 123 GB`, `[ok] PCIe: 3.0 x16`, `[ok] CPU … (AVX2)`, and `UD-IQ4_XS needs ~48 GB RAM: fits with 55 GiB of its experts in RAM, the rest read from the SSD`). It is not a preview of what the configuration will do — the configuration hands it four cards and its own settings.
- **Build** (host `ops/strata-build/`, receipt in `ops/reports/20261011-strata-trial/`): clone, `git checkout` the pinned revision, then their own Dockerfile with `--build-arg CUDA_ARCHITECTURES=86,89 --build-arg BUILD_VISION=0` (the profile served text only, until the encoder image above). One overlay layer is added on top: `chmod a+w /opt/strata`, plus the OCI `revision`/`source` labels the controller pins against. The engine's `BUILD.json` inside the image reports `archs [86, 89]`, `vision none`, `version 0.1.43`. The `-vision` image is the same recipe with `BUILD_VISION=1` and `runtime/overlay/` added as a second layer; its `BUILD.json` reports `vision gpu`, and that build script refuses to tag an image whose `/opt/strata/engine` has no `strata-vision` in it, because an image without the encoder starts, serves and reports healthy exactly as one with it.
- **This backend runs as the image's own user, and not as the deployment user** (since 2026-10-12; every other backend in the house keeps the unprivileged `1000:1000`). The `chmod a+w /opt/strata` above is not enough: the engine installs its Python packages into `/opt/strata/.venv` on first start, which the overlay left root-owned at 755, so as the deployment user it died 1.3 seconds in with `PermissionError: [Errno 13] Permission denied: '/opt/strata/.venv/.strata-pip.json'`. It is stated as `runs_as_image_user` on the engine entry, which renders the service with no user at all, and the observer accepts the empty string the daemon reports for it as matching. This is a wider grant than anything else the controller starts — the container gets the image's privileges — so it is on the engine, where it can be read and removed, and not inferred.
- **The family it is told to use is `unsloth`, not `qwen`** (changed 2026-10-12, after two runs that produced nothing). The staged shards are Unsloth's UD-IQ4_XS; with `FAMILY=qwen` the setup stops at its second step — `[X] Qwen3.8-Flash-Next has no UD-IQ4_XS model file`, `Setup stopped.` — and the container exits in a second, which from a terminal watching a counter is indistinguishable from a very slow model. With the family the engine itself names for that quant, setup reaches step 5 and starts hashing the 94 GB already on disk instead of downloading anything.
- **Cards.** `GPUS=0,1,2,3` and `LAYER_SPLIT=auto`: the four LLM cards, placed by Strata by free VRAM, and unchanged since the first boot. `CUDA_VISIBLE_DEVICES` is `0,1,2,3` on a host with no shared vision GPU and `0,1,2,3,4` on one that has one — the renderer appends the fifth card, and `VISION=yes` with `VISION_DEVICE=4` starts the encoder there. The container numbers the cards it was given in the host's bus order, so index 4 is the RTX 3080 and the encoder's own child process is started with `CUDA_DEVICE_ORDER=PCI_BUS_ID`; that is why the host has to state `vision_cuda_device` and why a value that is not the last reserved index is refused at render. With the encoder the catalog publishes `input_modalities: ["text", "image"]` and `capability_profile.vision: true`; without a vision GPU on the host it publishes text, which is what the backend serves. `memlock` is unlimited and the stop grace period is 180 s. It never co-resides with a llama.cpp backend: it is solo, so the everyday resident is stopped and the coding resident is recreated in its place.
- **Not enabled in the configuration:** `--calibrate` and any auto-tuning, and a second slot. `VISION` is stated `no` by the profile and turned on by the renderer on a host that names a vision GPU. The strict-determinism measurements (single-thread, cache-off) belong to the benchmark harness, not to the served configuration.
- **What `output_policy: unrestricted` means here.** The house contract requires it, and it is true in the sense it is used: the deployment sets no server-side output ceiling. It is **not** a claim that this quant produces unrestricted content: `UD-IQ4_XS` is Unsloth's dynamic quant of the official Qwen release, not an uncensored variant, so `nsfw` stays `false` and a warning to that effect ships with the catalog entry. It has not been attested on the trial quant.
- **Retention, bounded when it was created** (the rule is repeated in the configuration's `retention` block, and since 2026-10-18 it is stated once, on `flash-next-strata-solo-thinking-recovery`, for both configurations of this engine): the image — keep exactly the registered tag for as long as any configuration of this engine is registered, superseded tags removed reference-aware and never by a blanket prune (the 0.1.44.1 evaluation is the one exception, and a dated one: two Strata tags are registered from 2026-10-15 until the candidate is decided, when the losing entry and its tag go, reference-aware); the model revision — retained only while a configuration that mounts it is registered, then it is an ordinary library revision under the normal pass; the workspace `ai/strata-trial/data` — bounded by the engine and removed when the last configuration that mounts it goes; retiring a variant releases nothing it shares, which is what made it safe to retire three of the five Strata names on 2026-10-18 while a sibling went on mounting the same 94 GB of shards; reports — `ops/reports/<date>-strata-trial`, following the existing reports aging. Root filesystem headroom is checked before and after the download (the 85% warning line in the house maintenance pass); at staging it was 434 GB free of 938 GB.
- **Before selecting it:** see [the switch preparing the trial](#the-switch-prepares-the-trial-itself-and-what-the-measurements-still-do) — the switch builds the workspace itself, beside the serving model, before it drains, and waits for the engine's actual answer; the page shows on the configuration what the selection will do, and a refusal, if there is one, comes with the evidence it rests on. Switching back **is** the rollback; teardown is removing the configuration and then the image reference-aware.

## The switch prepares the trial itself (and what the measurements still do)

The trial was switched to four times on 2026-10-12. The first attempt failed on merged container settings. The second (01:12) got the container up and spent its whole readiness window inside the engine's first-boot work — reading 94 GB of shards, building the expert pack, installing the draft layer — never reached `/health`, and was abandoned with the router drained. The third (17:42) was the first to get the switch past the drain: the engine's server came up and its own health check passed while the model was still reading, so Docker — and `up --wait` — called the load done in about two minutes, the controller's one-shot verification saw the slot list still empty, aborted the switch, and the restoration put the previous profile back in 43 s. The fourth (18:47, with the wait in place) proved the wait: the switch re-observed on its own cadence while the engine reported it was reading, and when the engine stopped itself mid-read with the cards free and the kernel quiet, the switch failed at once instead of spending the window, and the restoration put the previous profile back in about two and a half minutes. The engine's own account of the stop was in a log inside the container, and the restoration deleted it — so the failure record now carries the state, the exit code, and the last words itself, read while the container still exists. The readiness window on this engine was never a measurement; it was 3600 s because that was a plausible number, and `up --wait` was not the thing that waits it out.

What the host measurements then showed, 2026-10-12:

- The first-start state — the 94 GB shard verification pass, the expert pack, the MTP draft — is written in **under ten minutes** (559 s to the point of no return, 7.9 GB into `/data`), and the served model never noticed: `neighbour_slots_max_seconds` 0.003 s against a 0.002 s baseline, its health never leaving `healthy`, card memory unmoved, MemAvailable flat at 66 GB. **Packing beside a loaded model is not the danger; the load is.** Once the state exists the engine immediately reads the whole model onto the four cards, and with llama.cpp holding them it dies exit 1 at `starting the engine: reading the model's weights`.
- The two runs before that never built anything at all: the engine exits in 1.3 s when the profile names the wrong family for its files (`--family unsloth`, not `qwen`), and as the house user it cannot write its own image's venv (`PermissionError: /opt/strata/.venv/...`), so the engine entry states `runs_as_image_user` — a wider grant than the house's, stated on the engine rather than inferred. And when it did build, the run waited for a ready file under the name the other family would write: the declaration is now a pattern (`config/strata-*-ud-iq4_xs.json`), the receipt records the path it matched as `ready_paths`, and a container that stops by itself ends the run in seconds with its own last words in the receipt (`container_log`) instead of being polled for two hours.

The design that grew out of that: **selecting the configuration is the operation.** A switch to a self-provisioning engine

1. **builds the workspace itself, before the drain** — the half that is safe beside a loaded model (measured above), in its own `preparing` phase, through the same throwaway project the read-only tool uses: same image, entrypoint, arguments, environment, user, binds and four card reservations, different container name and published port, service aliases dropped, its own project name so teardown can only ever reach its own leftovers. If the engine cannot build the workspace, the switch stops at the edge of the transaction: no drain, no touched backend, and the error carries the engine's own last words.
2. **drains and loads as any switch does**, waiting for the engine's actual answer. An engine like Strata answers `/health` with `status: ok` from server start — the model state rides in its `loaded` field, and `/slots` returns nothing until the read completes — so Docker being healthy is not the model being resident, and `up --wait` alone is not the wait. `readiness_wait_seconds` is the bound on the controller's own re-observation (every 15 s) until the slots report the contracted window. A loaded engine on the wrong window, or any other drift, is not waited out: the failure record carries the per-role differences, the slot window the engine reported, and — when the engine stops by itself, the one failure that leaves no health and no slots behind — the state, the exit code, and the engine's own last words, read while the container still exists because the restoration that follows removes it. The switch's bounded-generation acceptance still has to pass.
3. **records the boot it just waited** — the seconds the switch waited become the receipt's `warm_boot_seconds` / `healthy_warm_boot` (`via: switch`), so after one successful switch the measurements exist without anyone having taken them.

The only refusals left are the ones the machine's evidence backs, and they happen before the drain:

- a warm boot that was measured and **failed** (`never completed a warm boot from its own workspace`) — the honest move then is to fix or retire the configuration, not to spend a drain and a restoration relearning it;
- an engine that **stops itself at startup** — a configuration fault, reported in the words the engine gave.

Everything else is a **note**, not a refusal: `python3 -m runtime gate --profile <name>` (read-only, nothing locked, nothing drained, exit 1 only on a refusal) reports `reasons` and `notes` — the workspace still needs building (and how long the last build here took), a readiness window thin against a measured boot — and the page shows the same verdict on the configuration itself, from the per-configuration `reasons`/`notes` in `/api/status`, before the selection is made. A thin window is worth knowing; it is not paperwork, because the switch waits for the answer and the recovery path stands behind a switch that turns out to be wrong.

The read-only tool remains for evidence and diagnosis:

```sh
docker exec local-ai-runtime python3 -m runtime provision --profile flash-next-strata-solo-thinking-recovery
# build phase: throwaway project, beside the serving backend; nothing stopped

docker exec local-ai-runtime python3 -m runtime provision --profile flash-next-strata-solo-thinking-recovery --phase warm
# boot phase: refuses while anything is serving; it never stops the serving backend to get the cards
```

Runs from the tool and runs from a switch merge into one receipt, `.state/provisioning/flash-next-strata-solo-thinking-recovery.json`: engine tag and image id, workspace, ready files, `provision_seconds`, `warm_boot_seconds`, `healthy_warm_boot`, `pack_bytes`, `disk_free_bytes` before and after, `neighbour_healthy`, `neighbour_slots_max_seconds`, `ready_paths`, and every run with its samples and `via` (`cli` or `switch`). A receipt counts only for the image id and workspace directory it was taken with, so a rebuilt tag or a moved workspace invalidates it. The health answer is read from the container's **name on the router network** — the route the controller uses for every backend — with the published loopback port as fallback; `health_via` records which one answered, because a measurement taken through a route that does not exist would report an engine that never came up.

Teardown between attempts is `compose down` on the provisioning project name and nothing else — never a blanket prune, and never the serving stack's project.

## What the trial measured in its first day of real traffic (2026-10-14)

Sources, all of them the machine's own words: the engine's durable log `ai/strata-trial/data/strata-engine.log` (**771 served requests** from one boot, 11 hours of live agent traffic), the config the engine generated for itself, `/v1` engine info, and `tools/strata_bench.py --long` recorded as `data/bench-results/baseline-2026-10-14/`. Nothing below is estimated; every number is one recorded request or one engine line.

- **The layout the engine chose** (boot lines): `layer split auto: K=5,26,37`, so CUDA0 (RTX 3080 Ti) runs layers 0–4, CUDA1 (the RTX 3090, 23.56 GiB) layers 5–25, CUDA2 layers 26–36 and CUDA3 layers 37–47 plus the head — **predicted 27.5 ms per decode window**, with "the caches hold 16571 of 24576 profiled pairs (**~96.5% of the routed mass**), best of 15180 placements". Expert cache `auto`: **16,420 resident experts, 37,877 MiB** across the four cards (1,895 / 7,563 / 3,812 / 3,150 slots).
- **The storage hierarchy is not in the serving path, and the RAM budget is over-provisioned by design.** Setup asked for `--resident-budget-gib 55` (the pre-flight's "fits with 55 GiB of its experts in RAM, the rest read from the SSD"), and the engine allocated a **32.90 GiB** page-locked complement instead — because the GPU tier already holds everything but 18.44 GiB of experts. Across all 771 requests: **`0 blob reads from the file`**, and cumulative **expert cache hit rate 98.84% over 367,631,500 lookups** with 0.0% of routed experts read over PCIe. KV is `k8v4` with `--kv-resident 32768` and streaming on: **96.96% of 17.2 M block reads hit VRAM** in the longest sessions.
- **PCIe is fine.** The probe reports 8.0 GB/s host→device and sets `pcie_frac 0.22` (default 0.55), which makes a cache miss cost ×2.51; `nvidia-smi` shows all four cards at **Gen3 x16**, so the probe is the measured single-stream direction and not a lane fault. Speculation is `--spec 4 --spec-min-p 0.5` on an 835 MiB draft layer, accepting 73–76% in production.
- **Two of the engine's arguments are hand edits, not profile settings.** `strata-unsloth-ud-iq4_xs.json` differs from its own `.bak-original` by `allowed_hosts`, the durable `log` path, and **`--vram-reserve-mib 2048`**. They survive because nothing has reinstalled; see the reachability note below.

**The floor lives in the tail, not in the median.** Overall decode median 110.7, p10 99.7, p90 124.9, max 155.5 — and **65 of the 620 long generations (10%) fell below 100 tokens per second**, with p10 at 98–99 in every bucket above 64K. The owner's reading of "108–109" is the median at working context. There is no 8% of headroom to spend on a longer session: **the tail is already at the floor**, and the useful work is raising it.

**Prefill, not decode, is where this machine spends its time: 12,487 s of prompt processing against 5,656 s of generation (2.21×), and 11,577 s of that prompt time — 94% — is in requests that reused less than half their prompt.** Fresh-prompt throughput rises with the size of the read (879 tok/s at 4K, 1,685 at 16K, 2,171 at 32K from the recorded suite; 2,415 median on 50K+ fresh reads in production), and small reads are poor: 241 tokens cost 0.92 s and 917 cost 1.90 s, because the engine chunks prompts at 8,192 tokens (`prompt chunk auto: 8192 tokens, a 96-slot ring`). The bench's own agent-session cache hit is 68.8%.

**That 94% is upstream's benchmark and this box does not reproduce it.** It is quoted from the engine's own tip text -- `setup.py` advertising the conversation cache as saving "re-reading ~90% of their prompts (#882 #440)" -- and it was measured on upstream's workload. Measured here, over 7,196 requests and 75,911 s of prompt time in one resident's own engine log, the default `--prompt-cache 6` is already giving back **88.3% of prompt tokens** (11,896,394 of 13,478,599), and what is left splits into two piles that want opposite things:

- **6.3% of prompt time (4,764 s) is a conversation being read again that has already been read.** Five prompt sizes revisited three or more times each, 207 requests, and the largest single line is one 126,614-token prompt read from scratch 54 times for 2,614 s. That is the pile a parked conversation is for, and it is 6.3%, not 94%.
- **25.5% of prompt time is a prefix cliff.** `reused` stops dead at one of three constants -- 11,563 / 11,221 / 11,225 tokens -- while the prompt it belongs to grows past 130,000, and not one of the 111 candidate runs grows monotonically, so it is not checkpoint eviction thrash: something above the checkpoint cache has decided these conversations have ~11.5K reusable tokens. Parking restores an exact prefix and buys this pile nothing. It is the largest single block of prompt time on the machine, and it is an open question rather than a lever.

Meanwhile 4,118 requests already reuse more than 90% of a prompt of at least 16K. Any claim about prefill saved on this box is quoted against those two numbers from now on, not against 94%.

**`bench.sh` is the instrument for the next round — for prefill, and not for decode.** `/opt/strata/bench.sh` is a wrapper for `tools/strata_bench.py --long`, which drives the HTTP API of the already-running server (`--url http://127.0.0.1:8080`, `--out` into the durable workspace) and takes about three minutes. **Prefill repeats within ±0.6% and decode does not repeat at all: 4.9% across three runs, and the silent run was the slowest of the three.** Pooling the 108 agent-decode samples from the three runs (64 to 146 tok/s, CV 17%) and bootstrapping the median puts the 95% interval at **±6% for the sample size this tool produces** — so at three runs the suite cannot resolve a 4% decode change, and route tail skip costs 4–10%. The cause is in the tool's own README: "the conversation uses the model's own replies, so token counts differ a little between runs" — different text means different draft acceptance, and acceptance drives decode directly (73–90% in production). It is a load generator, not a fixed replay.

**What that means for the protocol is a split, not a verdict.** The conversation-cache and prefill experiments are prefill-shaped, so this suite is the right instrument for them and its ±0.6% is sharp enough to see them. The decode levers — pipeline windows, route tail skip, adapt-async — need a replay that resends identical text so acceptance is held constant, which is what a recorded Bench Studio session does and what `strata_bench.py` deliberately does not. Two cautions stand regardless: the short-chat decode cell spans 64 to 140 tok/s and is no signal, and the suite's `quality` subcommand computes nothing — it writes two temperature-0 answers out to be read by a human.

**One method rule, learned the hard way.** The engine under test is the engine answering the session that runs the test, so any prose generated while the suite runs is load on the measurement. A run is taken with the session silent, in one blocking call, and the log window either side is then audited for foreign requests — the silent run's window held 40 requests, all of them the suite's own, with no large one among them.

**The fixed replay is that missing instrument now, and this is what it measures.** `scripts/strata_replay.py` resends identical greedy text so draft acceptance is held constant; recorded 2026-10-14 as `data/replay-results/replay-baseline-2026-10-14-1922/`, five cells over six rounds with the first round reported apart as cold:

| tool-4k | 170.2 | [169.2, 171.7] | 881.4 | 4.58 s | 99.4% |

**Decode is dominated by cache warmth, not by context length.** The first pass over a prompt decodes 30–60% slower than every pass after it with time-to-first-token unchanged (code-4k: 112.5 cold against 164.0 warm), so round 1 is never pooled with the rest. Warm decode here is 148–170 where the recorded `bench.sh` figure is 104–109: two regimes of one engine, and only replay-against-replay in the same regime means anything.

**What the answer hash proves, and how far.** Inside one run it is a determinism proof: five samples of a cell that hash alike were decoded identically five times, which is exactly how `STRATA_HC_Q8` was shown not to be bit-identical below. Across runs it is weaker than it looks, and the weakness is upstream's rather than this harness's — greedy on this engine is not automatically reproducible, because the prefill MMQ path can settle the same prompt on different expert routes between passes, and with `STRATA_PREFILL_MMQ=0` it is bit-identical (Niko1221/Strata#2685, open: the same report as the greedy default, whose other half became a configuration here). Nothing in a results file records which of the two the engine was doing that day, so an answer hash that moves between two runs is a question about the image and its environment before it is a finding about the change being tested; the environment of both runs has to be named, as the recorded suites' does not, because `STRATA_PREFILL_MMQ` is not among the twelve variables the engine is told about.

**Sharp inside a run, soft between runs: about 1% within one run and about 2% from one run to the next.** The same four cells moved 161.1→164.0, 168.3→170.2, 156.0→155.7 and 146.7→148.1 across two runs, so a lever has to clear roughly 3% rather than 1% — and a bootstrap interval taken inside a single run cannot show that, which is why two runs per side are the unit of comparison.

**A third greedy run three days later says the engine is the engine.** `data/replay-results/greedy-20261017/` repeats the recorded suite on the image in service, after the overlay rebuild and a `sampling` block in the run config: 164.0→161.8, 170.2→164.2, 155.7→153.8, 159.6→157.4 and 148.1→140.6 -- between −1.2% and −5.1%, three of five outside the recorded bootstrap interval, mean about −2.5%. Two things matter in that table and neither is the speed. Every greedy answer hash came back **bit-identical** on all five cells, which is the result the request-level override is supposed to produce and the reason a resident now serving at the card's preset still has a comparable greedy arm three days and one rebuilt overlay later -- and, against the MMQ caveat above, one observation in favour of this box being reproducible rather than proof of it. The drift itself is a few percent of decode on a box whose ambient load differs from 2026-10-14, within the band this page already allows between runs; a real lever still has to clear ~3%, and this run is why that threshold gets re-listened to rather than assumed.

**The floor is on the cold path.** Cold decode came back at 112.5 for code-4k and 100.7 for prose-32k, so the owner's 100 tok/s floor is met with about one token per second to spare exactly where a fresh session first meets the engine. That is the argument for taking the accuracy-positive `STRATA_HC_Q8` before any lever that only moves the warm median.

**Three guards the live box taught the harness.** Cells are sized from chars-per-token measured against the served tokenizer (code 3.836, prose 4.726, JSON 2.183 — a uniform guess built a cell named 128k that was 208,561 tokens and was refused as over context); every sample records whether `/slots` was already generating, and a run taken over foreign work exits as "not a baseline" rather than as a slow run, with `--require-quiet` making idleness a precondition so an unattended run either gets its baseline or says why it did not; and a cell whose median answer is under 60% of `--max-tokens` fails, because a task that stops at 35 tokens produces a full table of plausible numbers that measure nothing.

**The first lever measured came back negative, and the instrument is the only reason it was caught.** `STRATA_PREFILL_AUTO_MAX=16384` — inherited on a list of free wins — was deployed and measured twice against the recorded suite: 4K **+0.3%**, 16K **−5.5%**, 32K **−5.9%**, with run-to-run drift of 0.06–0.16%. It was reverted. The mechanism was already visible in the boot log: the ceiling was never the limit, `auto` took 9216 tokens either way, and the larger chunk borrows more expert-cache slots to hold its buffers (6,933 against 6,281). Fewer resident experts on a box reporting `pcie_frac 0.22` costs more than the re-streaming it saves, so anything that lends experts to the prompt path has to be weighed against the experts it evicts rather than the chunk it enables. Worth noting what the old resolution would have done with this: a 5% prefill change on an instrument that repeats within 0.2% is unambiguous, and the same change against the suite's ±6% decode spread would have been filed as noise and the flag left in place.

**The second lever was also a loss, and it was caught on an axis the suite does not measure at all.** `STRATA_HC_Q8=1` reads the hyper-connection projections from the GGUF's Q8_0 bytes. It booted on all four cards and came back at mean decode **+1.1%** — under the 3% the replay resolves between runs, and negative on two of five cells — against prefill **−8.2% to −15.5%** and first token **9–18% slower**. Q8_0 bytes are wider than the quantized ones they replace, so the prompt path pays for them on every token it reads, on the box that reports `pcie_frac 0.22`. Reverted. The decisive evidence was not the speed: the replay hashes greedy answers, and they changed (the code cell stopped at 156 tokens where the baseline ran to 256), so the flag is not bit-identical and its accuracy benefit is unproven rather than established. An unproven accuracy gain does not buy a 15% prefill loss; if accuracy is to be bought, it should be bought with a measurement of accuracy.

**What is and is not reachable from configuration on this engine.** The Strata engine's `environment` map carries twenty-one entries -- the thirteen it had (`--family`, `--quant`, `--kv`, `--kv-streaming`, `--vision`, `--vision-device`, `--gpus`, `--layer-split`, `--low-ram`, `--host`, `--port`, `--sampling`, `--tool-call-recovery`) plus `--conversation-cache-mib`, `--conversation-cache-min-free-mib`, `--conversation-cache-slots`, `--conversation-cache-min-tokens` and `--ple-gguf`, plus `--rope-scaling`, `--rope-scale` and `--yarn-orig-ctx` added on 2026-10-18 -- and nothing else. Eleven are settings the engine is told about on its own command line. One is a preset name this house's entry point reads and the engine never sees, one names a key the engine reads out of its run config but has no argument for, the five added on 2026-10-17 are arguments the engine does have but is not told about on the command line, and the three added on 2026-10-18 are the position ring a rope-scaled window is read through -- all of it: the entry point edits them into the argument list of the run config instead, because that is where the engine looks for them. All ten therefore reach the engine only as a line this house's entry point writes into that file, which is why an image without the entry point refuses a profile that states any of them rather than quietly ignoring it. Everything else the running command line shows (`--spec 4`, `--mtp`, `--max-context`, `--kv-resident`, `--resident-budget-gib`) is written by the image into `config/<quant>.json`. That file is not regenerated at every boot, which is what this page claimed until 2026-10-17: a normal start rewrites it from the file it just loaded, and a setup pass carries over every key it was not asked about -- `sampling` is named in that carry-over list -- so a hand edit survives the next start. That is worse than being erased, not better: it is invisible to the controller, it cannot be rendered from a profile, and it goes with the workspace, which is why all three facts above are written by the entry point on every start instead. That closes off the last argument that looked like a config change: `--pipeline-windows 2` passes all eight of its refusal conditions here -- `--serve`, four distinct stages, MTP drafter present with `--spec 4`, no `--batch`, no `--peer-device`, no helper caches, and `adapt_async` defaulting to 0 -- but there is no variable that reaches it, and `STRATA_PIPELINE_AUTO` cannot help, because on a non-HIP build the auto path assigns `on = false` unconditionally, so that variable can only ever turn the feature off. What was stated there as a plain consequence stopped being true the same day, and the reason it stopped is worth keeping straight, because it changes what "we cannot reach that" means from now on. Nothing in this house could write a key the engine reads out of its own run config, so run-config-only settings landed on the image side of the line. The entry point edits that file's argument list now, which moves `--conversation-cache-*`, `--ple-gguf`, `--adapt-async` and even `--pipeline-windows` to the reachable side -- a profile, a rebuild and a drain each, no new engine build. What replaced the barrier is worse rather than better: reachability is no longer the reason a lever sits unswitched, measurement is. `--pipeline-windows 2` still passes all eight of its refusal conditions and `adapt_async` still assigns `on = false` unconditionally on a non-HIP build, so that variable can only ever turn the feature off; `--adapt-async 1` answers differently from run to run, which would buy a drain for +6% nobody has measured on these cards. The two that survived that sorting are no longer rows in a table of ideas: they are configurations -- `...-full-route` and `...-cache`, each one variable from the configuration before it, each refused at render time if it cannot be honoured and one switch from being undone.

**What a request that sends no sampling used to get.** A request that names no sampling gets the backend's own default, and until 2026-10-17 the two backends this house has run disagreed about what that means. llama.cpp is started with `--temp 1.0 --top-p 0.95 --top-k 20 --min-p 0.0`, which is the Qwen3.8-Flash-Next card's thinking-mode set; Strata, given no `sampling` block in its run config, decodes greedy -- its own server says so ("An absent temperature keeps the engine's default, which is greedy") and its setup never writes the block. The router forwards an omitted temperature as omitted rather than inventing one, and this house's coding agent sends none, so every routed request to this resident was decoded at the one setting the card does not recommend, and at the one that reproduces a verbatim repetition loop deterministically when the model falls into one.

**`--sampling` closes it, as a name and not as numbers.** The numbers live in `runtime/overlay/strata-vision-entrypoint.sh`, which writes the block into the run config on every start: `thinking` is the card's thinking-mode set (1.0 / 0.95 / 20 / min_p 0.0, no penalties), `instruct` is its non-thinking set (0.7 / 0.80 / 20 / 0.0 plus `presence_penalty` 1.5, which the engine does not apply inside batch windows), and `off` takes the block back out. Names rather than numbers because the engine refuses to start on a sampling value it does not understand -- a `SystemExit` at start, and for an exclusive resident that is nothing serving -- so a value outside the table is refused when the profile renders, before any drain, and the boot that does run prints the numbers it wrote. Only an image carrying this house's entry point can be told a preset: the text-only Strata tags run upstream's entry point unchanged, and a profile that names `--sampling` on one of them is refused rather than ignored.

**It shipped as a second configuration, not as a change to the one in service.** On 2026-10-17 `flash-next-strata-solo` stated `--sampling off` and decoded the way it always had; `flash-next-strata-solo-thinking` stated `thinking` and decoded the way the card and the llama.cpp residents do. They were the same image, the same shards, the same workspace, the same window and the same service IDs -- `AVariantIsOneLineApartFromItsOriginal` rendered both and refused the pair the moment anything but the sampling variable differed -- and the portal listed them apart by variant label, `greedy` and `card sampling`, because their display names are legitimately identical. The reason for the pair was that this resident is exclusive and it is the thing the agents are typing to: a change to it is a drain the agent performs on itself, and the rollback of a change this cheap has to be cheaper than the change. Going over was an operator act at the portal and coming back was the same act in the other direction -- no checkout, no deploy, no edit, and nothing for the agent under it to survive. **The greedy arm was retired on 2026-10-18**, a day after it was measured: one sampling policy for the whole house is the position, the pair had served its purpose of making the move reversible, and a configuration nobody is testing costs a rendered launch, a chain step to keep honest and a row an operator reads as a decision. The preset is still stated rather than omitted: the run config lives in the workspace, which outlives both configurations, so a profile that names nothing would leave the thinking block sitting there being read by the greedy configuration that follows it. The pair shares that one workspace, which the provisioning invariant normally refuses, because same engine and same shards means the same pack -- a workspace of its own would buy a second copy of a tens-of-gigabytes pack and an hour of nothing serving on the first switch, for a directory that comes out identical.

**`tool_call_recovery` was the second switch, and it is the base configuration now.** This model sometimes writes a call to a declared tool in a form beside the template's -- `<parameter=NAME>` as the opener, JSON inside `<tool_call>`, a bare `<function=NAME>` at the start of a line outside code, or a second call inside the same wrapper -- and while the key is off the engine reads those four as prose, which for an agent is a turn that looks like it did something and did nothing. Upstream measures 92.9% of agent turns' tool calls read as intended with the key off against 98.3% with it on, over 1,462 turns of this model under a coding agent, and puts the calls its own parser dropped at 5.4% of turns. That is upstream's corpus, and it is no longer the only one: `scripts/transcript_loops.py --dropped` reads this house's own session store for the two things a dropped call cannot help leaving behind -- the call's markup in an assistant message that got no call, outside a code fence or a backtick span, and any step that ended in the parser's own `malformed tool call` error. Over 163 sessions and 16,702 turns that wanted a tool, every one of them served without the switch, the rate is **0.0%**: nothing arrived as prose carrying a call, and nothing died of the parse. The instrument is not blind -- the store does hold the markup, twice, quoted in a fence by an agent writing about this parser, and both occurrences went to the quoted column. So the 5.4% upstream found is not a tax this box was paying, and what this configuration buys here is insurance against a failure that has not occurred, exactly like the sampling step before it. So it ships exactly as the preset did -- `flash-next-strata-solo-thinking-recovery` states `--tool-call-recovery on`, sits one variable from `flash-next-strata-solo-thinking` under the same chain check, and is labelled `card sampling + call recovery` in the portal. It is a parser over the tools a request itself declared, run while the reply streams, so it costs nothing on the decode path and a request with no tools is unaffected; the failure it can add is a call where the model meant to quote one, guarded by the same fence-and-line logic that already guards the template's own form, and upstream found no instance of it. The image that carries it was built the same day, `16ffa1282a12…`, and until the revision that pins that id is deployed a container still runs the image before it, which ignores the variable exactly as the sampling image did before its own rebuild — so the first boot of this configuration is checked by its log line, not by the fact that the portal accepted the choice. (That id is now `local/strata:296b59d2f73c-vision-pre-cache`: the tag was rebuilt later the same day to carry the two switches below, and the id the engine entry pins is `761cafff21bc…`. Both switches are in one image, and the recovery switch is readable in that image's entry point, which is the only proof of it this house has. Rebuilding it is not `docker build` alone: the house layer has to re-declare `org.opencontainers.image.revision` with the source and trial labels, because Strata's own Dockerfile labels only the NVIDIA base and four paths -- the switch guard, the update cutover, the migration check, the recovery path -- read that revision back out of `docker image inspect`. The rebuild that forgot it built cleanly, was refused at the deploy gate as `pinned inference engine identity changed`, and cost the press of a button and nothing else, which is the shape this house prefers a mistake to take.)

**The next two steps were measures, and both have now been paid for.** `flash-next-strata-solo-thinking-recovery-full-route` -- retired on 2026-10-18 the day it was declined, with `STRATA_ROUTE_TAIL_SKIP=0` the only thing it existed to set; re-adding it is a profile file and one chain step, and the paragraphs below are the warning it would have carried -- set `STRATA_ROUTE_TAIL_SKIP=0` in the container environment -- an upstream variable, read with `getenv`, which is why it is the one of the two that needs no image rebuild and runs on the image already deployed. The hypothesis was that this box sits on the wrong side of the trade the skip makes: the engine drops a route it would have to miss, 96.1% of the missed expert entries in the trial were dropped that way, upstream prices the drop at KL 0.003--0.006, and upstream's own code turns the skip off when the expert cache runs near full because there it costs draft acceptance (70.1% to 68.2%) and 1--2% of decode instead. Measured on 2026-10-18 against the same configuration with the skip left at its default, it **does** drop what it says it drops and it is **not** measurably costing this box anything. With the skip on, 94.8% of route-tail misses since the start (91,811 of about 97,000) never reach the PCIe path and the engine's expert-cache windows report at most 284 reads; with `STRATA_ROUTE_TAIL_SKIP=0` the skip line is never printed at all and the same windows report 1,942 and 2,878 -- the mechanism, moving about sevenfold, confirmed from the engine rather than from the environment. And the speed axis it claims is the one axis this instrument cannot see: prefill came back the same to within 0.5% (4K, 16K and 32K prompt tok/s, three runs each), while two quiet bench runs of an *identical* configuration disagree by 10--30% on every decode-type number it produces, so neither upstream's +10--20% -- which its own help text prices for ``12-16 GB cards that miss experts``, on a resident whose expert cache hits 97--99% -- nor the cost of taking the whole route is resolvable at the bench's sample size. So it is declined rather than disbelieved, which for this house is the same outcome as the 0.0% dropped-call rate and the same rollback: the default stays the default, the configuration stays selectable one switch away, and its `deployment_warnings` now carry the numbers instead of the hypothesis. What no instrument here weighed is the thing the flag actually trades against, the KL 0.003--0.006; a speed bench that cannot see an axis is not evidence that the axis does not matter.

`flash-next-strata-solo-thinking-recovery-cache` does need the rebuilt image, because the conversation cache reaches the engine as four keys in its run config and only this house's entry point can write them. It states a 16,384 MiB budget above a 12,288 MiB floor, two slots, and a 16,384-token minimum -- sized from this box's 6.3% of prompt time rather than from the 94% this page used to quote, with a floor placed above the 32.93 GiB page-locked expert complement rather than competing with it, and with the minimum keeping a short side request out of a slot holding a 126,614-token conversation. Measured the same night, and **selected**: it is what the resident is running now. `scripts/strata_park_probe.py` drives three conversations of 76,620 to 92,688 tokens in rotation with 18-second gaps, so every one of them comes back to find its slot taken by the others. First sight of a conversation is 76,620 tokens read in 31.6 s. A turn that returns to a parked conversation is 87,302 tokens of context with 5,363 read in 6.4 s, and the engine's own log says so in the same breath: `conversation cache: restored 81939 tokens (checkpoint) in 135.2 ms`. That is **5.1x off a resumed turn**, bought by a park costing 200--820 ms and 1.7--2.6 GB, 6.46 GB in all across two parked conversations against the 16 GiB budget. Two slots served two of the three conversations and the third re-read its entire prefix (81,944 of 81,944, 81,973 of 81,973), which is precisely what a slot is worth and precisely how many of them buy: raising `--conversation-cache-slots` is a decision against `--conversation-cache-min-free-mib` and this box's RAM, not a default to move unmeasured, so the shipped configuration keeps the two slots it was measured with. `/metrics` is the running instrument -- `conversation_cache` `{"enabled": true, "budget_mib": 16384, "parks": 18, "restores": 9}` after the probe against `{"enabled": false, "budget_mib": 0, "restores": 0}` before it, with `bytes` never passing the budget -- and `off` remains one switch away.

**The benchmark could not have found any of that, and that is worth a paragraph of its own.** A benchmark run keeps the conversations it is measuring hot in a RAM slot, which is the one condition a conversation cache does not help; the same bench that is blind to the park shows prefill within 0.5% and an agent cache hit of 67.88 against 67.85, and would have reported the purchase as nothing. The measurement protocol that did work, in the order it mattered: one thing talks to the model at a time, because a single background conversation occupies one of six prompt-cache slots and evicts the run's own sessions -- the first baseline read 0.00% agent cache hit and 30,274 tokens re-read per session while the identical quiet run read 68.81% and 3; `prompt tok/s` and the agent cache hit are the engine's own statements and repeat to about 0.5%, while every metric that measures *time the request waited* moves by up to sixfold with unrelated traffic and is one-sided; and `scripts/strata_bench_compare.py` pairs the per-request samples and prints a bootstrap 95% CI with the word `invisible` when the interval spans 1.0, so a reader is not left to infer from a ratio of medians that something was measured. Use it for anything this bench has to decide.

**What it costs, and what it does not buy.** Measured upstream on this model with `--spec 4 --mtp`: draft acceptance 81.2% to 72.7% and decode 0.94x (CI 0.83-1.23) over 114 short requests, and about 76% to 72% acceptance with 62 to 59 tok/s on UD-IQ4_XS, this resident's quant. Not accuracy: 26/30 against 25/30 exact answers and 15/15 against 15/15 valid tool calls in the same A/B, and zero repetition loops in either arm. What it buys is the card's own policy, one policy across the house, and the end of a failure mode that is deterministic when it does happen. `scripts/strata_replay.py --sampling thinking`, run against the thinking configuration, is the arm that prices it on these cards; it has been run, and what it came back with is below, because the first number it gave was wrong for a reason worth writing down.

**The sampled arm is measured, and it is cheaper than this suite can resolve.** 2026-10-17, both arms back to back on the image in service so the pair is same-day and same-cache: `data/replay-results/greedy-20261017/` as the control -- `temperature 0` in the request, five cells, six rounds, `--require-quiet 30 --retries 4`, exit 0 -- against `data/replay-results/sampling-thinking-20261017-clean/`, the same corpus at the thinking preset. Warm decode moved **−0.4%, +0.5%, −0.2%, −5.1%, −0.4%**: median −0.4%, four of five cells inside the control arm's own bootstrap interval, and the fifth (`prose-32k`) a point estimate whose sample spread covers the control's whole interval. Draft acceptance moved from 94.8% to 94.3% pooled, cell by cell 94.7→93.3, 95.9→95.9, 93.4→93.4, 98.6→99.2, 91.5→89.7. Neither arm repeated a line four times over.

**Why that number is a floor and not the price.** These cells enumerate strings copied out of their own prompt, so the next token is near-certain and sampling has almost nothing to choose -- the distribution is peaked, acceptance survives, and a token or two of difference in a 256-token answer is the whole mechanism available to cost anything. Upstream's 0.94x was taken over short mixed requests, where it showed up as acceptance 81.2% to 72.7%; acceptance here did not fall, so the corpus did not reproduce the condition that produces the cost. The honest statement is a bracket: what the thinking preset costs this box is between what this suite can see, about half a percent, and upstream's ~6%, and real agent turns are high-entropy enough to sit nearer the upper end than the cells are. The suite bounds the price; it does not settle it, and nothing in it says the switch was wrong -- a median half percent of decode is not a reason to keep a resident off the model card's sampling.

**A first attempt at that run, an hour earlier, is the operational lesson.** `data/replay-results/sampling-thinking-2026-10-17/` exited 3 with eleven of thirty samples taken while the engine was already generating, and its −6.7% to −21.4% was a queue rather than a decode delta. The contamination was the session that started the run: an agent measuring its own engine is inside the thing it is measuring, so `--require-quiet` holds the *start* until the box is idle and cannot hold it idle. The clean pair above was taken in a gap in traffic with the driver saying nothing until both arms had returned. It also corrected one claim from the contaminated table, which is worth keeping because it is the kind of claim that survives if you do not re-measure: the two distinct `prose-32k` answers that "proved the preset was reaching the sampler" did not reproduce -- the clean sampled arm answered every cell identically five times, exactly as the greedy control did. That this corpus cannot tell the two arms apart textually is the same peaked-distribution fact as the decode result above, seen from the other side; the evidence that the preset is in force is the engine's own `/props` and boot line, not a replay.

**The loops themselves were looked for at home, and are not there.** `scripts/transcript_loops.py` reads this house's own DSH session store and counts runs of identical consecutive tool calls in the order the agents made them -- #1560's method -- with one addition, because the cheap version of that count lies in a specific direction here: a run counts as a stall only when the repeated call also *answered* identically. Over 157 sessions and 18,697 tool calls, all of it served greedily by this resident, no session reached a run of 4, the longest run anywhere was 3, and every one of them was a `job_output(wait=true)` poll taken while a background job ran, which returns something new each time and is an agent waiting rather than an agent looping. So this box was not paying a repetition tax that the sampling change removes. What the thinking configuration buys here is the card's policy and one policy across the house, against a failure mode this store has not caught happening -- which is an argument for the switch being cheap rather than urgent, and the honest version of the sentence above about a deterministic failure mode. Nor is 18,697 calls proof of absence: the same scan against the sampled side needs days of traffic before it says anything at all.

**Two things do not move, and one of them is every number above.** A request that brings its own sampling still wins, and both of this house's instruments do: Bench Studio pins `temperature: 0` in every built-in profile and the replay sends `temperature: 0`, so every recorded measurement here is a greedy arm and stays one -- still comparable with itself, and no longer describing what production does. And going back to greedy is selecting `flash-next-strata-solo` again -- one drain, no edit and no deploy -- which takes the block out of the workspace instead of leaving it there for the next configuration, or a text-only image, to go on reading. Upstream has the same feature open as PR #1274 (`--thinking` / `--instruct` setup flags, opt-in, default path unchanged) as of 2026-10-17; when it merges, the table in the entry point goes and the profile states the engine's own flag. `reasoning_loop_recovery` stays off: it fired zero times in both arms of that A/B, and its `recover` mode additionally needs the xhigh effort sentence in the first system message.

**And the suite agrees with production, which is what makes it trustworthy and what corrected one of the levers above.** The suite's fresh 4K prompt measures 882.5 tok/s; production's fresh reads averaging 4,019 tokens measure 881 tok/s. Laying the two side by side, effective prefill throughput is strongly sublinear in the size of the read:

| Fresh read | 469 tok | 1,335 | 4,019 | 13,649 | 20,943 | 53,014 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |

That is a 7× spread, and it is *not* a constant per-request cost — a fixed-cost-plus-rate fit over 229 fresh reads leaves 1.3 s of median residual and predicts the small buckets badly. What follows for the chunk cap is narrower than it first looked: reads below 8,192 tokens are a single chunk and the cap cannot touch them, so `--prefill auto:16384` is an experiment about the 13K–32K range only. **The lever that removes whole 25-second reads is not making prefill faster but not doing it: the conversation cache, which the engine leaves off by default.** It has now been measured on this box and selected -- `flash-next-strata-solo-thinking-recovery-cache` is the resident, and `scripts/strata_park_probe.py` is what decided it: a 76,620-token conversation first costs 31.6 s of reading and returns later, through a parked checkpoint, as 5,363 tokens read in 6.4 s. The 6.3% of prompt time this page computed from the log is the share that is *eligible*; what an eligible conversation actually gives back when it comes back is the 5.1x above, and the two numbers answer different questions.

**The three questions the owner asked, closed against this evidence:**

1. **A 3-bit pack has no value here, and the reason is measurable rather than theoretical.** Hit rate 98.84%, zero file reads, 96.5% of the routed mass already resident: there is no memory-system pressure for a smaller pack to relieve. And the routed experts are the small part of a decode window — upstream's breakdown puts them at 4.2 ms of 34.3 ms, with the dense Q8_0 side "about 4.8 GB in every file" regardless of quant. Upstream's yardstick against Q8_0 (4,995 teacher-forced positions) puts `UD-IQ4_XS` at 88.91% same-top-token / KL 0.101, `IQ3_S` at 87.69% / 0.144 and `IQ3_XXS` at 84.46% / 0.202. 3-bit is a pure accuracy purchase of a non-bottleneck. The accuracy direction that *is* open is the other way: `UD-Q4_K_XL` at 93.09% / 0.056, for 16 GiB more experts.
2. **128K buys nothing.** The window costs RAM (2.2 GB of `k8v4` KV at 160K) and not decode; `--kv-resident 32768` is what bounds the VRAM and it does not move with the window, which is why the measured curve is flat. Dropping the advertised window to 128K saves about 0.5 GB of RAM and nothing else.
3. **The ceiling is 262,144, it was admissible, and it is what ships now.** The deployed router `c3a342b` carries `RESIDENT_CONTEXT_LIMIT = 262144` with the comment "256K window of the Qwen3.8 models. The runtime controller owns per-profile qualification", the model's native `context_length` is 262,144, and `ROUTER_CONTEXT_LIMIT` in `runtime/config.py` agrees. Above it needs YaRN scaling and leaves the contract. On the measured curve the window itself is worth ~1–2 tokens per second; **what bounds it is the tail, not the ceiling** — at 100–131K actual context p10 is already 98.1. The ladder below walked the window from 160K to that ceiling on 2026-10-18 and found the curve flat all the way to it. *Amended the same night:* after the factor ladder under **"Beyond the ladder"** measured what the rope carries past that edge, the contract moved -- LLM Router `0d9dc83` widened `RESIDENT_CONTEXT_LIMIT` to 524,288 and `ROUTER_CONTEXT_LIMIT` followed it in the same coordinated release, and the first rope-scaled window crossed on `flash-next-strata-solo-thinking-recovery-cache-yarn`. What shipping at that number took, and what the trial is watching, is **"The 2× rung, shipped as a trial"** below.

**How these are reached is a real constraint, not a detail.** `STRATA_*` variables and the already-mapped ones go in the profile's `container.environment` and are rendered by existing code with no new mechanism. `--prefill` is mapped in neither direction, and `--pipeline-windows`, `--adapt-async` and `--expert-profile*` have **no environment variable in the entrypoint at all**: they exist only inside `ai/strata-trial/data/config/strata-unsloth-ud-iq4_xs.json`, which is the engine's own state, is what the entrypoint starts from on every fresh container, and is invisible to the controller except through the slot window it reports. Seven statements do have a route now: this house's own entry point (`runtime/overlay/strata-vision-entrypoint.sh`, whose header states each fact it carries) writes the encoder's card, the sampling preset, the tool-call recovery switch, the conversation-cache budget, the PLE table and — since 2026-10-18 — the session window into that file on every boot, from the profile's environment, and `tests/test_provision.py` runs the real script against a stub workspace for each of them. `REINSTALL=1` regenerates that file from the environment and discards the edits that have no such route; the ones the entry point writes it re-asserts, which is what "the profile is the authority and not the file" means in practice. **A tuned argument that earns its place has to end up declared in the profile — the same way `--vram-reserve-mib` should have been — or it is one reinstall away from silently gone.** Each of them is a drain to apply: the warm boot now measures **115.3 s** and provisioning 1.6 s against a 3,600 s readiness bound, so an experiment is cheap, and the agreed circuit breaker (under 8 GiB MemAvailable, or under 150 MiB free on any of the four cards) still means switching back rather than debugging. One thing the route does *not* do is re-tune: setup.py's stored calibration is keyed on a hardware key that includes the context, so a *future* setup pass over a widened workspace spends its 15–30 minutes again.

**What is still unmeasured, and which instrument closes it.** Every number above is speed, and the trial has never been through Bench Studio — the 27B configurations each carry "a full Bench Studio coding session (2/2 passed)" while the trial carries a catalog warning that its output "has not been attested on this quant". Three instruments, at three prices, and they are not interchangeable:

- **`bench.sh` (`tools/strata_bench.py --long`)** — the speed gate, for prefill. Three minutes, attaches to the running server, needs no drain, repeats within ±0.6% on prompt throughput and time-to-first-token. **Its decode cells repeat only within about ±6%**, so they rank nothing that trades 4–10% of decode; run it silently and audit the window, because the session driving it is served by the engine it is measuring.
- **Bench Studio** — the only scored instrument on this machine, and the one that decides whether a change is *allowed*. It is not part of Strata and not a dependency of any speed experiment; it is needed for exactly one class of decision, the ones that buy speed with accuracy, of which route tail skip (96.1% of missed experts skipped, active right now, never measured here) is the only known instance.
- **Strata's own gates, both needing a GPU window rather than a measurement slot** — `bench/bench_vs_llama.py quality` generates the same two prompts from both engines at temperature 0 and writes them out **to be read by a human; it computes no score**, so it is a cheap greedy-output diff and no more. `tools/conversation_cache_parity.py` is the real thing — a full-model A/B/A parity gate over the engine's internal state — but it loads private engines sequentially and "requires an available GPU/model-loading window", i.e. a drain, and it is dry-run by default.

The order that follows is therefore set by what each decision needs: the speed-only levers go through `bench.sh` and cost nothing but a drain each; route tail skip waits for a scored run, because there is no honest way to price 4–10% of decode against an accuracy cost nobody has measured on this box.

## The session-size ladder (2026-10-18)

Widening the session is the one lever on this box that buys **capacity** rather than speed, and the question was how far it goes before it starts costing something. Four rungs, one deploy each, one number each: **163,840** as it stood, then **196,608**, **229,376**, **262,144**. Multiples of 16,384 rather than round numbers, because the pack's pages and prompt chunks are powers of two; the top rung is the number `ROUTER_CONTEXT_LIMIT`, the router's `RESIDENT_CONTEXT_LIMIT` and the model's native `context_length` already agree on, so the ladder ends where the contract ends rather than one rung short of it. A rung above this one is not a slower session, it is YaRN scaling and a different contract.

**What each rung is.** One line in the profile — `context_tokens` — and it moves **both** configurations of this resident together, because the engine's run config is one file per workspace: two configurations of one resident that disagreed about the window would turn a switch between them into a resize, 115 s of drain to change something the operator did not switch. The one-variable rule between them is what forces the pair to move as a unit, which is the rule working as intended. Everything else the rung touches is bookkeeping the house insists on: the two digests per configuration in `tests/fixtures/renamed-profiles.json`, re-pinned from the render rather than typed, and the launch catalog in `tests/test_controller.py`, whose `(192K)` label is computed from `context_tokens`. `git revert` and a normal update is the whole rollback: the same route rewrites `--max-context` back down.

**Adding a rung later** is one line per configuration, twice — `context_tokens` and the caveat sentence that states the capacity — plus the digests and the catalog label the same commit has to move, and `python3 -m unittest discover -s tests` says whether anything else was counting. What is *not* mechanical is that a rung is a drain and a warm boot: 115 s of warm boot against a 3,600 s readiness bound, and a switch that reads `/slots.n_ctx` against the promise before publishing, so a rung the engine cannot hold is restored rather than served. One thing the route still does not do is re-tune: setup.py's stored calibration is keyed on a hardware key that includes the context, so the first future setup pass over these workspaces spends its 15–30 minutes again, and no rung of this ladder ran one.

## Service restoration: the host never rests with nothing serving

Every destructive transition on this host has to be survivable without a person, and the path that
puts the machine back has to be exercised by tests against the failures the deploy paths can
actually produce. This house is run by agents. A human in front of a drained router with no lever is
the failure mode, not the fallback.

So the runtime never comes to rest with no backend serving and no automatic action pending. Either a
healthy backend answers with admissions open, or the last-known-good release is being brought back —
now, or on a schedule that does not need anyone at the keyboard.

### What that means when a transition fails

| Situation | Behaviour |
| --- | --- |
| A backend's `/slots` cannot be fetched | It is serving nothing. It is recorded as `unreachable` and never holds a drain open. A response that is not a slot list is recorded as `malformed`, which is not evidence of work either. |
| A drain deadline passes during a restoration | The restoration continues. The router already rejects everything, so there is nobody left to be polite to; aborting there is exactly how a host ends up drained with no backend. |
| A drain deadline passes before any backend was replaced | The operation refuses and has touched nothing. A generation on a backend's own port is legitimate work, and backing away costs nothing yet. |
| A deployment fails after replacing a backend | The previous release is restored through the same finalize path a healthy boot uses: recreate, verify health and generation, republish the catalog, undrain, write the receipt. |
| That restoration fails too | The next attempt is scheduled on a capped backoff (30s, 60s, 2m, 5m, 10m, 15m) and the controller's supervision loop takes it up. Attempts continue until the service comes back. |
| The router rejects a newly published catalog | Publication restores the prior catalog before backend recovery checks drain ownership. The failed catalog must not disable the admin API that recovery uses. |
| The router admin API fails before restoration can begin | The failure advances the retry count and backoff, including failures while checking drain ownership. |

The failure is never left as a condition to notice. `.state/restoration.json` is the durable action:
the configuration to bring back, how many attempts have run, the reason, `next_attempt_at`, and the phases
reached. It is cleared only once a healthy backend is serving with admissions open, and it holds off
`python3 -m runtime.recovery export` while it is outstanding. Each phase a restoration reaches is
also written into `transaction.json` under `restoration`, so what an attempt did is readable
afterwards without a journal.

### Three ways to run the same restoration

There is one implementation — the boot-time path that brought this host back on llama.cpp by itself
after the 2026-10-12 outage — and three ways to reach it:

| Way | When it is used |
| --- | --- |
| The supervision loop | Automatic. A restoration that has come due runs on its own and the page reflects it. |
| **Restore last-known-good** in the runtime page (`POST /api/restore-last-known-good`) | The one action for a machine that is not serving. It names no configuration and expects nothing to have been observed first, and appears on the page whenever the runtime is not serving. |
| `docker exec local-ai-runtime python3 -m runtime restore` | The same call from a shell, including one the browser cannot reach. |

All three hold `runtime.lock` for the whole pass, refuse a router release that has reserved the
runtime, and refuse to start while another operation is running. They do not refuse a runtime that
is mid-transaction, not ready, or already reporting failures — that is the moment restoration is
needed. A drain left set by an attempt that stopped belongs to no live operation, so the
restoration takes it over and clears it.

`GET /api/status` carries the contract: `service` (`serving`, `restorable`, `pending`, `profile`)
and `restoration` (attempts, reason, next attempt, phases). Raw Docker errors stay in the private
journals; the browser is shown the shape of the failure, never its text.

### The release gates

`tests/test_restoration.py` is what keeps this honest, and it runs in CI as part of
`python3 -m unittest discover -s tests -v`:

- a target that starts but never becomes healthy → the previous configuration is restored inside the
  same call, the router is undrained, and a healthy backend is serving;
- the restoration's own first attempt fails → it is scheduled, re-entered, and succeeds with nobody
  touching anything;
- a `/slots` response of the wrong shape → a bounded wait and a recorded decision, never a hang;
- a backend that answers no port at all → treated as idle, so the drain can settle.

## Recover an interrupted update

```sh
cd /home/astigmatism/apps/local-ai-runtime
scripts/recover-update.sh
```

Recovery requires clean source and an expected revision. It reads the durable update and runtime journals, restores an interrupted runtime transaction when needed, and recreates only the controller using the recorded active image. This clears stale Docker health results from a temporary revision mismatch and applies a fresh bounded readiness wait. If the candidate runtime already succeeded, it completes controller replacement and source advancement without applying the models again. If the previous runtime is restored, it keeps source changes for an explicit retry. It never discards local work.

For a runtime operation interrupted outside the portal updater:

```sh
docker exec local-ai-runtime python3 -m runtime recover
```

If the controller is unavailable, use the already installed candidate image and the same mounts as the updater. From the host checkout:

```sh
python3 - <<'PY'
from pathlib import Path
from runtime.config import read
from runtime.update import Updater
updater = Updater(Path.cwd())
transaction = read(updater.state / 'transaction.json')
updater.candidate(transaction['target']['image'], 'recover')
PY
```

A failed initializer may sit in Docker's restart loop while recovery runs. That no longer stalls it: a backend whose `/slots` cannot be read is serving nothing, and once the router reports it is relaying no work the restoration continues rather than arguing about activity it cannot see. If a pass still fails — a protected backend has drifted, a router release has reserved the runtime, or the release cannot be brought up at all — the attempt is recorded and the next one is scheduled, and the runtime page offers the same restoration as one action. Read the failed backend's logs when a specific backend needs repair, then run the restoration; admission stays paused until verification succeeds. `needs-attention` now means an attempt failed and another is coming, not that the machine needs to be restarted.

## Restore the initial host controller

Use this only to undo the initial migration before a subsequent runtime release or configuration change:

```sh
scripts/migrate.sh restore
```

It requires the initial revision/profile and healthy matching backends. It stops only the new controller, restores the saved host files, removes runtime ownership, and restores the original startup-unit enablement. It does not stop the model servers or remove persistent data. If initial cutover stopped after creating its backup, retain that directory and inspect the failure before running restore; do not delete it to force a fresh cutover.

## Boot verification: separate reboot window

Docker owns controller/model restart supervision after cutover. The controller serves diagnostic status while waiting for Docker, backend health, the existing network, and the router. Its startup operation is idempotent. It refuses stale revisions, interrupted runtime transactions, and unfinished router maintenance.

During an agreed reboot window, verify that the selected configuration remains unchanged, every GPU its residents use is assigned correctly, each loaded service passes health checks, router discovery reports the correct aliases/context, the controller becomes healthy, and DSH/Open WebUI can still reach the router. The existing network is preserved; no boot command destroys or recreates it. This test is not performed by staging or by a normal update.
