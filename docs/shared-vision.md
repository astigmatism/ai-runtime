# Optional shared vision GPU

Hosts without `vision_gpu_id` keep CPU vision and the original two-device backends. In `.state/host.json`, set `vision_gpu_id` to a full UUID outside both `gpu_ids` pairs, optionally set `vision_gpu_name`, and supply `cuda_order.daytime` and `cuda_order.nighttime` with the two text UUIDs in their existing CUDA order. Runtime appends the shared vision UUID as CUDA2 and exports that three-UUID `CUDA_VISIBLE_DEVICES` list. The four text UUIDs remain exclusive.

Use [the complete host example](../config/host.shared-vision.example.json) as a reference. Replace every synthetic UUID and example path with verified host values; do not overwrite an existing host configuration with the example. Its ordering represents the `daytime` pair's CUDA0 = RTX 4080 SUPER, CUDA1 = RTX 3090; the `nighttime` pair's CUDA0 = RTX 4080, CUDA1 = RTX 3080 Ti; both append RTX 3080 as CUDA2. Hardware identities, paths, and credentials remain private deployment settings. Profile arguments, renderer behavior, and validation belong in version-controlled source.

The existing CPU defaults in profiles remain authoritative for installations without this opt-in. With it enabled, rendering changes only projector offload, GPU visibility/reservations, and corresponding discovery metadata: `--mmproj-offload --mmproj-device CUDA2`. Text model devices, tensor overrides, KV cache, and MTP devices must remain on CUDA0/CUDA1 (or existing CPU tensor overrides). Both llama.cpp engines already support this option.

The Strata engine is a separate case, because its encoder is not a projector loaded inside the serving process. It is a second process (`strata-vision`, llama.cpp `mtmd`) compiled into the image with `BUILD_VISION=1`, and it is placed by the `cuda_device` key of the `vision` section of the engine's own run config, which has no command-line flag. The image that carries it is tagged `local/strata:<revision>-vision`; the renderer lends it the shared card the way it lends a projector one — `vision_gpu_id` in host settings opts the host in, the profile keeps its text-only `--vision no` default, and the container gains the fifth GPU with `VISION=yes` and `VISION_DEVICE=<index>`. An entrypoint overlay in this repository (`runtime/overlay/`) writes that number into the run config on every start, because nothing upstream can be told it. The overlay also owns the section's existence: the engine's setup pass is the only writer of a `vision` section, and the upstream entry point runs that pass only when the workspace has no config at all — a workspace installed without vision keeps a text-only config forever and would serve without its encoder, visibly nowhere (2026-10-16). So where the config has no `vision` section, the overlay runs that pass itself — the upstream entry point's exact setup arguments, `--no-start`, the profile's model arguments from its own environment — and only then writes the card; a config that still has no section afterwards fails the boot instead of serving text-only. An image built without the encoder maps no `--vision-device`, so the renderer leaves the shared card out of its container entirely: the same profile on such an engine is the text-only backend it was, given no card it cannot name.

A solo configuration (`"exclusive": true`) on a llama.cpp engine requires this setting. It reserves both text pairs as CUDA0–CUDA3 in `gpu_ids` order (the `daytime` pair, then the `nighttime` pair; `cuda_order` is not used) and the vision GPU as CUDA4. A model that owns every text card of its host loads nothing else — a configuration cannot name a second model beside an exclusive one — so the vision GPU is shared with nothing and may also carry that model's MTP draft; text tensors still never use it. An environment-configured configuration takes the same devices for its own text card count, and the encoder's number is derived from that count: the shared card has to be the last one reserved — the card the text GPUs leave free — and the renderer appends it there and numbers it `len(text_devices)`, which is CUDA4 for a solo configuration and CUDA2 for a two-card one. Since 2026-10-20 that derivation is what places the encoder, not the host's `vision_cuda_device`: one host states one host file, and it can serve both layouts, so the same card cannot have one number in it. The host key remains as the solo number for whoever reads the file, and a value that is not an integer is refused at render as the typo it is. `flash-next-strata-solo` has run that way since 2026-10-16; on a host with no `vision_gpu_id` it renders as the text-only configuration it was, and its catalog entry publishes text modalities. See [exclusive solo configurations](deployment.md#exclusive-solo-configurations).

Each backend loads its own projector. This is shared hardware, not a separate encoder service. CPU image preprocessing remains normal. The catalog identifies `text_gpu_uuids`, `vision_gpu_uuid`, `vision_device`, `vision_gpu_shared`, and `cuda_visible_devices`; `gpu_uuids` contains all reserved devices. `cuda_visible_devices` states what the container was told in the notation it was told it in — a UUID list on an argument-vector engine, an index list on an engine addressed by index — and `vision_device` is the number the encoder was placed at in that notation. Runtime status separates text and vision hardware. Live readiness checks validate the UUID order as well as the device reservation.

Before enabling on another host, measure simultaneous and repeated image requests, maximum supported inputs, retained buffers, and profile changes. Encoder file sizes do not predict peak VRAM. Independent router queues do not coordinate vision memory. If coexistence fails, restore CPU configuration; do not silently shrink contexts or images.

For source changes, edit and test on the development Mac, commit and push `main`, then select **Update and restart** for AI Runtime in Service Portal. The updater fetches published source, exports an immutable candidate, builds with `SOURCE_REVISION`, runs tests and validation, drains accepted work, deploys the candidate, replaces the controller, and advances the production checkout only after health checks pass. Never edit production source, build from uncommitted production files, or change active revision receipts to bypass safeguards. Keep prior host configuration, image, and source for rollback. Read [deployment and recovery](deployment.md) for recovery operations; direct candidate deployment is not the routine release path.

The host's `.state/host.json` is intentionally excluded from Git and image builds. An ordinary update preserves it, so the selected vision GPU remains enabled across releases. This is not a local source modification. Generic hosts remain CPU-only unless they opt in. After an update, confirm clean production `main`, matching `origin/main` and deployed image revision, Runtime readiness, and CUDA2 projector placement. A controller-only release with unchanged rendered configuration preserves the existing inference containers.

To return to CPU, remove `vision_gpu_id`, `vision_gpu_name`, and `cuda_order` from host settings and run `apply` with the current controller. Runtime drains accepted work before replacing affected backends. Removing host settings alone does not change a running backend. Do not terminate active generations on drain timeout. For the Strata engine the same removal is the whole rollback: the image keeps an encoder it is no longer given a card for, and reverting to the text-only engine entry is a profile change, not a rebuild.
