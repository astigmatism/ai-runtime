# One router, more than one machine

A runtime owns its models, qualifies what it loaded, and tells a router about them. This document is that boundary as it is built: what a machine sends, when it sends it, what counts as proof it arrived, and what a machine may not assume about the router on the other end. The router's half lives in `llm-router/docs/RUNTIME_INTEGRATION.md` and `MULTI_HOST.md`; where the two disagree, this file says what the runtime does and why, and the disagreement is a bug in one of them.

It replaced a design that said routers pull, written on 2026-10-20 and built by nobody. That design deserves one paragraph rather than a museum: it was right that a machine must stay the only author of what is live on it, and wrong about who opens the connection. A pull makes the router a client of every machine — it has to reach each runtime's port through every Host allowlist, and it has to decide what a document means when a fetch went stale, which is how three rules about freshness and two clocks appeared in a document about publishing a list of models. Publication is not a state to be observed, it is an event that happens when a configuration changes. The event is sent, the router says which revision it accepted, and nobody needs to know what time it is. The boundary moved to the router, and a boundary quietly worked around in one implementation is worse than one amended in the open.

## What the runtime sends

One document, the same one the local router has always read: `schema_version` 3, `default_model`, `models[]`, the `configuration` object, and the default model's fields projected onto the root. No pointer to it, no subset of it, no wrapper — the router reads a pushed document with the reader that will later serve it, including the attestation that a model's output and thinking limits are genuinely absent, so a document that survives validation is a document that can be served.

- **When:** with the backends verified, inside the switch, before the drain is released — so a client is never told about a model that is not yet resident — and again at startup once the backends verify, which is what puts a catalog back after a router restart or a machine rebuild without waiting for someone to change a configuration.
- **Where:** `PUT /admin/api/hosts/<host_id>/catalog`, bearer token in the header, the token's *name* in `.state/host.json` and its value in the container's environment. `host_id` is stated once, in the machine's own settings; the target is a URL and a credential, because a machine cannot speak as anybody but itself.
- **Receipt:** the revision in the response, compared and recorded. `200` without a revision is a failure. The revision is what the router computed from the bytes it accepted, so a runtime that compares it is publishing on proof and one that does not is publishing on optimism.
- **Refusal:** a router that refuses an invalid catalog keeps serving the catalog it accepted, so a failed publication is a deployment that did not happen rather than a house with no models. `409 CATALOG_ID_CONFLICT` names the service IDs another machine already answers; `404 HOST_NOT_DECLARED` says this machine's id is not in the router's list. Both fail the switch, because a catalog nobody can address is the worse failure.
- **Retirement:** `DELETE` when the machine stops serving these models. A catalog whose backends nobody starts is a 503 with a promising name in front of it.

## What the runtime may not assume

**The router's `available` is a fact about the router's network.** A router two hops away reports a backend unreachable when it cannot open `backend_url`, which for most of this migration is exactly what it should say: the backends were published on loopback, for a router that read a file on the same box. So unreachability is refused only by a machine that has claimed a routable address — `backend_address` in its settings, which moves the Compose port binding and the advertised URL together — and is otherwise recorded as a warning on the status page beside the machine's own health. A router that cannot reach a backend is never a reason to call this machine unhealthy, and a page that conflates the two gets a machine rebooted for somebody's routing table.

**A router's model list is a fleet's list.** On a shared router the models it reports are every machine's, so verification asks about the ids this machine published and no others. Same for `active_model`: it names the model an unnamed request receives, which is the default host's answer, and a machine that is not the default must not fail its own switch because another machine's model is the one on offer.

**A drain belongs to one machine.** `POST /admin/api/runtime-drain {enabled, host, reason}` pauses this machine's admissions and leaves its neighbours serving. What a machine waits for before touching a backend is work *for this machine* — `active_by_host` and `queued_by_host` — and what it refuses to do while a neighbour is draining is nothing at all. The reason still travels with the drain, and still decides whose drain it is: a pass that cleared a drain it did not set would let the setter's clients reach a backend being replaced.

**Aliases are a fleet-wide name, so they must not collide.** A service ID is one machine's to answer. `daytime` and `nighttime` are Rosalina's residents and `daisy` is Daisy's; the router refuses a catalog that takes a name it has already given somebody else. `local-active`, which used to mean "this machine's active model" on every machine, is published only by the entry the router answers unnamed requests with — the default host's. That is a change to the profiles, and it is the one part of this a machine cannot verify alone.

## Two routers, and the one that goes away

A machine can hold both sinks at once: `router_state_dir` (write the document, `POST reload-config`, verify) and `router_target` (push, verify). That is the migration state, and it is deliberate — Rosalina's clients are still on Rosalina's router, so a switch has to stay invisible to it while the new router is being proven. Both get the same document, and both get drained, because a switch that drains one router while the other is still admitting work is a switch that interrupts someone. The file goes first because it is the sink this runtime can put back exactly; the push needs no undo path, since a refusal there already left the accepted catalog in force.

The end of the transition is a decision with a date and not a default: clients repoint to the router on `.23`, someone stops the old router, and the clients notice if it happened early. Then `router_state_dir` leaves the host settings, the mount and the file write and `reload-config` go with it, and the `local-ai-ollama_default` network stops being a prerequisite for a machine whose only job is to publish. Until then, "published" means published twice, and the status page says which sink holds which revision.

While both are configured the two are not equals, and pretending otherwise gets the worst of both: a switch stopped dead by a machine nobody is serving traffic from, and a copy quietly a fortnight behind. So a push router that cannot be reached is recorded as a sink that has not caught up and the supervising loop hands it the document again on the pass after it returns, while a push router that *refuses* fails the switch exactly as the directory would — an unanswerable router is a router's schedule, a refusal is this machine's document, and only one of those improves by waiting. Nothing has to be told when this ends: the tolerance is a property of having a directory at all, and the same call becomes fatal the moment the setting goes away.

## A new machine, in order

Declare it at the router (`ROUTER_HOSTS`) and restart the router. Give it a `.state/host.json` with `host_id`, `gpu_architectures`, its own model root, `backend_address`, and a `router_target` naming the credential — [the example](../config/host.second-machine.example.json) is that file. Give the container the token in its environment: never in the repository, and never in `host.json`. The router's address lives in an environment variable, which is the only reason it is not in the code. Run a switch, and read the receipt.

A machine that states neither sink refuses to start. The failure it prevents is a runtime that begins, passes every health check, and tells nobody, with every metric green and the household without models.

## What this does not settle

Which machine owns `local-active` is the router's policy, and changing the default host while traffic is flowing is a switch in its own right, with the same drain rules and no drain of its own yet. The context ceiling a shared router advertises is now the ceiling of the union of every machine's catalog, so a widening is still router-image-first and controller-second — and now it is a widening for machines that did not ask. Daisy has no vision card to lend and publishes no vision capability, so anything that assumes a household vision endpoint has to be re-read now that two machines can answer. The router is one machine's process and it is not redundant: when it is down, runtimes switch freely and nothing reaches them, which is a worse-looking state than a runtime that refused to start, and worth a design of its own before a third machine makes it likely. And a router that has been told a machine exists, by an operator, and then never hears from it, currently waits forever — whether that deserves a staleness bound is the pull design's best question, and it still has no answer.
